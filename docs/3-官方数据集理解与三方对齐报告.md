# 官方数据集理解、产品匹配与三方对齐报告

> 审查对象：`data/`、`docs/1-设计文档.md`、`docs/2-开发-总体方案.md`。  
> 审查原则：PCAP 内容是数据事实；文件名只作为线索，不能替代结构化标签或攻击事实。

## Step 1：《官方数据集理解报告》

### 1. 总体结论

比赛方提供的是一套 **NTA（Network Traffic Analysis，网络流量分析）攻击流量样本集**。可以把 PCAP 理解为“网络通信录像”：它记录某段时间内哪些 IP 和端口进行通信、使用什么协议，以及未加密通信中传输了什么请求和响应。

数据集不是 CI/CD 事件集、云 API 审计日志、凭据状态库或资源费用记录。它适合验证网络流量解析、恶意请求识别、单个抓包内的通信时间线和证据回查，但不能单独证明 API Key 泄露与云资源滥用的完整攻击链。

### 2. 目录结构

```text
data/
└── 测评中心基线样本nta/
    ├── <32位十六进制ID>.json.pcap       1130 个
    ├── <长数字ID>.json.pcap              488 个
    ├── <攻击类型或工具名称>.pcap/...　   719 个
    └── 共 2337 个抓包文件
```

目录中没有 README、数据说明、字段说明、Schema、metadata、CSV、JSON、JSONL、标签表、样例代码或 baseline 程序。虽然 1689 个文件名以 `.json.pcap` 结尾，但实际读取确认它们仍是二进制 PCAP，不是 JSON。

### 4. 文件命名方式

文件名分为三类：

1. **32 位十六进制 ID**：例如 `003260...json.pcap`。名称不能说明攻击类型。
2. **长数字 ID**：例如 `16288557416613796.json.pcap`。可能是样本编号或时间相关编号，但没有说明文件，不能自行解释。
3. **描述性名称**：例如 `12.mssql_bool_tuoku.pcap`、`Gitlab_未授权上传RCE.pcap`、`Response_Command_high_whoami.json.pcap`。这些名称可以提示攻击工具、漏洞或行为，但不是独立标签字段。

对 719 个描述性名称做近似分类后，主要包含 WebShell/管理工具流量、SQL 注入与数据库利用、漏洞探测/RCE/反序列化、命令执行与系统探测、文件上传、反弹 Shell/隧道、弱口令等。分类之间存在重叠，不能把该统计当作官方标签分布。

### 5. 实际文件类型与内容

| 数据类型 | 是否存在 | 实际内容 | 可支持的任务 |
|---|---|---|---|
| PCAP/PCAP-NG | 是 | 原始网络包、时间戳、IP、端口、协议、载荷 | 流量解析、规则验证、网络证据回查 |
| JSON/JSONL/CSV | 否 | `.json.pcap` 仍是抓包 | 不能按结构化记录直接读取 |
| CI 事件 | 否 | 无 Action、Digest、Runner、Secret 访问结构化记录 | 需要 Synthetic 或未来真实连接器 |
| 云 API 审计 | 否 | 无稳定的 credential_id、cloud_action、resource_id | 需要 Synthetic 或未来云平台接入 |
| 凭据状态 | 否 | 无 Key 有效/冻结/轮换状态 | 需要 Mock/沙箱状态服务 |
| 资源/费用事件 | 否 | 无云资源创建和费用字段 | 需要 Synthetic + Mock/沙箱 |
| 端点事件 | 否 | 无进程树、主机账号或 EDR 事件 | 当前产品不依赖该数据 |
| 独立标签/ground truth | 否 | 只有部分描述性文件名 | 不能直接作为完整监督学习训练集 |

### 6. 代表性样本验证

- `16288557416613796.json.pcap` 实际包含 HTTP GET 请求，URI 中出现 SQL 注入表达式；可读取时间、源/目的 IP、端口、HTTP 方法、URI、Host、User-Agent、响应状态和响应正文。
- `jsp.pcap` 是 PCAP-NG，包含向 `/jspwebshell/cai1.jsp` 发起的 HTTP POST 及后续通信，可形成同一抓包内的 WebShell 会话时间线。
- `mssql_dnslog_xp_subdirs_192.168.10.11.pcap` 包含 DNS 查询，可观察查询时间、查询发起 IP、DNS 服务 IP 和域名。
- `Gitlab_未授权上传RCE.pcap` 除目标攻击通信外还包含 SSDP、DNS、TLS 等背景流量，说明“文件名指向攻击”不代表包内每条通信都恶意。

### 7. 主要字段及其现实含义

PCAP 没有统一的 JSON 字段表，下列字段需要通过流量解析器从网络包中提取。

| 可提取字段 | 现实含义 | 对产品的价值 | 限制 |
|---|---|---|---|
| `capture_id` | 当前抓包文件的样本标识 | 作为 EvidenceReference 的数据集内定位 | 由系统根据文件生成，不是官方事件 ID |
| `packet_timestamp` | 网络包被捕获的时间 | 排序、建立同一抓包内时间线 | 不同文件时钟是否一致无法确认 |
| `src_ip` / `dst_ip` | 通信发起方和接收方地址 | 识别来源、目标和异常通信方向 | NAT、代理和测试环境复用会影响现实身份解释 |
| `src_port` / `dst_port` | 通信两端端口 | 区分 HTTP、数据库、DNS 等服务 | 端口不必然等于协议，需结合载荷判断 |
| `transport_protocol` | TCP、UDP、ICMP 等传输协议 | 选择解析器并构建网络流 | 不能直接代表业务动作 |
| TCP flags/seq/ack | 连接建立、传输和关闭信息 | 重组会话、判断请求响应顺序 | 需要流重组，单包分析可能不完整 |
| HTTP `method` | GET、POST、PUT 等请求动作 | 判断请求类型和潜在副作用 | 只适用于可见 HTTP，不适用于加密 HTTPS |
| HTTP `uri` / query | 请求路径和参数 | 识别 SQL 注入、命令执行、文件访问等特征 | 不能自动等价为云 API 或合法/恶意结论 |
| HTTP `Host` | 请求的主机/虚拟站点 | 识别访问目标 | 测试样本中的 Host 可能与目的 IP 不一致 |
| HTTP headers | User-Agent、Authorization、Content-Type 等 | 判断客户端特征、认证方式和载荷格式 | 数据中出现的 Basic Authorization 不等于 API Key |
| HTTP status/body | 服务端响应状态和正文 | 判断请求是否得到响应、是否泄露内容 | 200 不等于攻击成功；部分响应需 TCP 重组 |
| DNS query name/type | 查询的域名和记录类型 | 发现 DNSLog、命令回连和外联线索 | 正常 DNS 与恶意 DNS 需上下文区分 |
| payload bytes | 原始应用载荷 | 支持深度检测和证据回查 | 加密、编码、分片或协议未知时不可直接解释 |
| `five_tuple` | 源/目的 IP、源/目的端口、协议组合 | 同一抓包内关联一条网络流 | 不是跨文件、跨系统事件 ID |

一句话解释：官方数据最擅长回答“网络上谁在什么时候向谁发送了什么可见请求”，不擅长回答“这个请求用了哪一个云 Key、属于哪个租户、创建了什么云资源、后来是否完成轮换”。

### 8. 协议与流量概况

- 解析到约 649,917 个 TCP 包、10,965 个 UDP 包和 262 个 ICMP 包；另有 ARP/IPv6 等非 IPv4 Ethernet 帧。
- 主要目的端口包括 80、8080、1433、3389、443 等，HTTP 和数据库相关流量占比较明显。
- 从未加密载荷中识别到约 37,908 个 GET、8,304 个 POST，以及少量 PUT/PATCH/HEAD。
- 数据中存在 HTTPS/TLS 流量。没有会话密钥时，只能分析连接元数据，不能读取加密后的 URI、Header 或正文。

上述数值用于理解数据规模，不等于恶意事件数量；同一请求会跨多个包，一个文件也可能包含背景流量。

### 9. 数据关联能力

#### 9.1 同一抓包内部

可以通过以下信息进行可靠程度较高的关联：

```text
capture_id
  + packet_timestamp
  + src_ip/dst_ip
  + src_port/dst_port
  + transport_protocol
  + TCP 序列信息
```

这可以把包重组成网络流或请求—响应会话，并形成“时间 → 来源 → 目标 → 请求 → 响应”的局部时间线。

#### 9.2 不同抓包之间

不能仅凭相同 IP 或相近时间把不同文件认定为同一攻击事件，原因包括：

- 没有统一 incident_id、trace_id、flow_id 或 session_id；
- 多个样本重复使用实验室私网 IP；
- 不同文件的采集环境、时钟和背景流量没有说明；
- 描述性文件名和不透明 ID 之间没有映射表。

因此，官方数据 **支持同一 PCAP 内的流量证据关联，但不支持可靠的跨 PCAP、跨 CI、跨凭据、跨云资源关联**。

### 10. 标签判断

数据中没有 `label`、`normal`、`benign`、`attack_type` 或 ground truth 文件。719 个描述性文件名提供弱标签线索，1618 个文件名不提供可解释类别；目录中也没有明确的正常样本组。

专业结论：

- 可用于人工抽样确认后的规则回归测试；
- 可用于构建“弱标签候选集”，但标签需重新核验；
- 可用于检测 Agent 的流量解析与证据定位测试；
- 不能直接声称可训练或评估一个监督式“正常/攻击”分类模型；
- 不能用该数据计算可信的整体准确率、召回率或误报率，除非团队先建立可审计标注集。

### 11. 数据 → 产品能力映射矩阵

| 数据类型 | 能提供什么事实 | 支持哪个产品环节 | 使用它的 Agent | 能否直接用于 Demo | 是否需要加工 |
|---|---|---|---|---|---|
| PCAP 包元数据 | 时间、IP、端口、协议、包方向 | 数据接入、异常来源、流量时间线 | 静默监测、事件调查、攻击溯源 | 可以，适合展示官方 Evidence | 需要解析、脱敏、生成 capture/packet 引用 |
| HTTP 明文请求 | 方法、URI、Host、Header、Body | 异常访问、恶意参数、接口行为调查 | 静默监测、事件调查 | 可以，但只能按其真实攻击类型展示 | 需要 TCP 重组、HTTP 解析和规则/模型抽取 |
| HTTP 明文响应 | 状态、Header、部分正文 | 请求结果和潜在信息泄露调查 | 事件调查 | 部分可以 | 需要响应重组；200 不能直接判定攻击成功 |
| DNS 流量 | 查询源、DNS 目标、域名、时间 | DNSLog、外联或回连线索 | 静默监测、攻击溯源 | 可以 | 需要 DNS 解析和上下文判断 |
| 数据库/其他协议流量 | 服务端口、连接、部分协议载荷 | SQL 注入、数据库利用调查 | 静默监测、事件调查 | 部分可以 | 需要协议解析，部分载荷不可读 |
| 描述性文件名 | 攻击工具/漏洞/行为提示 | 样本筛选、人工标注辅助 | 开发测试，不直接交给 Agent 定案 | 可作为“官方样本名称”显示 | 必须标注为弱标签，不能作为唯一 Evidence |
| 不透明文件名 | 样本唯一定位 | EvidenceReference | 全部只读分析 Agent | 可以用于回查 | 需要内容解析后才能判断类型 |
| TLS 加密流量 | 时间、IP、端口、长度等元数据 | 连接异常、频率和来源分析 | 静默监测 | 部分可以 | 无密钥不能解析 API 内容 |

### 12. 分产品环节判断

#### A. 静默监测

| 检测目标 | 支持程度 | 依据 |
|---|---|---|
| 异常来源 | 部分可以 | src/dst IP、端口和同一文件内通信方向可用；没有租户历史基线和地理/设备数据 |
| 异常访问 | 可以 | 明文 HTTP 方法、URI、参数和载荷可用于识别 SQL 注入、RCE、WebShell 等网络攻击行为 |
| 异常频率 | 部分可以 | 同一抓包内可按时间和五元组计数；多数文件只有 7 个包，不能代表长期基线 |
| 异常 API | 部分可以 | 可识别 HTTP 路径与参数，但没有“这是云 API”或接口业务目录 |
| 异常资源操作 | 不可以 | 没有 cloud_action、resource_id、resource_type、cost 等字段 |
| 异常认证 | 部分可以 | 少量明文 Basic Authorization 或登录流量可见；没有统一用户、credential_id 或认证结果日志 |

#### B. 事件调查

| 调查问题 | 判断 | 说明 |
|---|---|---|
| API Key 是否被使用 | 不可以 | 没有稳定的 API Key 标识；载荷中的 token/secret 字符串不能自动解释为本项目 Key |
| 什么时候使用 | 不可以（针对 Key）；可以（针对网络请求） | 有包时间，但无法绑定到 Key |
| 从哪里使用 | 部分可以 | 可以确定观察到的网络 src_ip，不能确认现实攻击者、Runner 或设备 |
| 调用了什么接口 | 部分可以 | 明文 HTTP 可见 URI；TLS 和非 HTTP 受限，且没有云 API 目录 |
| 是否访问敏感数据 | 部分可以 | 部分 SQL 注入/响应正文可能显示查询或泄露线索；不能证明租户云敏感数据 |
| 是否产生资源操作 | 不可以 | 没有云资源操作事件 |
| 是否造成云侧影响 | 不可以 | 没有资源状态、费用、权限或业务状态 |

#### C. 攻击溯源

官方数据可形成：

```text
时间 → 观察到的源 IP/端口 → 目标 IP/端口 → HTTP/DNS/数据库行为 → 响应
```

官方数据不能形成：

```text
CI Action → Runner → Credential ID → 云 API 身份 → 租户资源
```

缺失的是 CI 组件元数据、Runner 身份、凭据标识、租户/账号、云 API 审计和资源 ID。攻击溯源 Agent 可真实使用 PCAP 形成网络侧局部时间线，但主标杆事件的完整时间线必须由明确标识的 Synthetic 事件补齐。

#### D. 响应处置

PCAP 是历史离线记录，不能冻结、轮换或恢复任何凭据，也不能改变云资源。该部分必须由 Mock Adapter 或受控沙箱状态服务承担。把离线文件“删除”或“停止播放”不能算处置成功。

#### E. 恢复验证

官方 PCAP 只能作为“处置前已发生的攻击证据”，不能动态证明旧 Key 失效、新 Key 生效或业务恢复。建议采用：

```text
官方 PCAP：提供可回查的网络攻击证据（若用于该事件）
Synthetic：提供 CI、Key 标识、云 API 和资源影响事件
Mock/沙箱：维护旧 Key、新 Key、恶意调用、合法 CI 和资源创建的动态状态
```

### 13. 数据 → Agent 矩阵

| Agent | 官方 PCAP 使用方式 | 官方数据不能提供的部分 | 补齐来源 |
|---|---|---|---|
| 主代理 | 只读取已脱敏的 Signal、EvidenceReference 和子代理结果，不直接解析全部原始包 | CI/云业务上下文、策略和状态 | Synthetic + 系统状态 |
| 静默监测子代理 | 解析/消费流量事件，识别恶意 HTTP、异常来源、频率和 DNS/数据库线索 | CI Action、Runner、Key、云资源 | Synthetic 或未来真实连接器 |
| 事件调查子代理 | 回查指定 PCAP/流、请求和响应，确认网络行为事实 | Key 使用、敏感云数据、资源/费用影响 | Synthetic 云审计/资源事件 |
| 攻击溯源子代理 | 按时间和五元组形成同一 PCAP 内的网络时间线 | 跨 PCAP、CI—Runner—Key—资源链 | Synthetic 关联事件；未来真实多源数据 |
| 操作执行子代理 | 不使用 PCAP 执行动作，只可引用其作为申请依据 | 动态冻结、轮换、恢复 | Mock/沙箱状态服务 |
| 审计汇报子代理 | 引用官方 capture_id/packet/flow 证据和系统审计记录 | 执行与验证记录 | 系统审计 + Mock/沙箱回读 |

### 14. 攻击链数据覆盖表

| 攻击链节点 | 官方数据能否证明 | 对应文件/字段 | 缺失内容 | 建议解决办法 |
|---|---|---|---|---|
| 第三方 CI Action 被篡改 | 不支持 | 无 | Action、版本、Digest、权限变化 | Synthetic CI Security Event；未来接入真实 CI |
| CI Runner 读取 API Key | 不支持 | 无 | Runner ID、Secret 访问、Key 标识 | Synthetic Secret Access Event |
| API Key 泄露 | 不支持 | 无 | 外传事件、Key 指纹和泄露渠道 | Synthetic 泄露事件；不得生成明文 Key |

| 敏感数据读取 | 部分支持 | 部分 SQL/HTTP 请求响应 | 云数据分类、租户数据对象 | 如选用真实 PCAP，只表述其真实数据库/HTTP行为；主场景用 Synthetic 资源访问事件 |
| 高费用云资源创建 | 不支持 | 无 | resource_id、类型、数量、费用 | Synthetic 资源事件 + Mock 资源状态 |
| 系统发现 | 部分支持 | PCAP 解析后的流量 Signal | CI/云组合检测 | 官方 PCAP 可验证 NTA Signal；主事件组合信号需 Synthetic |
| 事件调查 | 部分支持 | 流量请求/响应和 EvidenceReference | Key、租户、资源影响 | 官方 + Synthetic |
| 攻击溯源 | 部分支持 | 同一 PCAP 时间戳和五元组 | CI—Runner—Credential—Resource | 官方网络时间线 + Synthetic 跨域时间线 |
| 冻结/轮换 | 不支持 | 无 | 动态凭据状态 | Mock/沙箱 |
| 恢复验证 | 不支持 | 无 | 新旧 Key 与合法业务动态结果 | Mock/沙箱状态回读 |
| 审计 | 部分支持 | capture 文件可作只读证据源 | AgentTask、审批、执行、验证记录 | 系统运行时生成审计记录 |

### 15. 数据与产品匹配程度

结论：**部分匹配，但主标杆攻击链存在结构性数据缺口。**

交集是网络流量的异常发现、局部调查、局部时间线和原始证据回查；错位是 CI、凭据身份、云 API 审计、资源/费用、动态处置和恢复状态。

#### 方案 A：保持当前产品与标杆事件

- 产品逻辑：保持唯一、成熟，不因数据集变成通用 NTA/SOC。
- 数据支持：官方 PCAP 用于流量连接器、Signal 提取、EvidenceReference 和规则/模型验证；CI/云事件用 Synthetic；执行验证用 Mock/沙箱。
- 开发难度：需要建设三种数据来源的清晰适配和标识，但边界可控。
- Demo 效果：能够展示完整闭环，但必须明确哪些画面来自官方、Synthetic 和 Mock。
- 比赛风险：官方数据不能独立证明主攻击链，评委可能质疑场景与数据匹配。

#### 方案 B：把标杆事件改为 Web 攻击/WebShell/SQL 注入闭环

- 产品逻辑：与当前 API 凭据产品定位产生实质变化，接近通用 NTA/SOC。
- 数据支持：检测、调查和网络溯源明显增强。
- 开发难度：需重新设计客户价值、Agent 内部工具、处置对象与恢复断言。
- Demo 效果：官方 PCAP 使用更充分，但冻结/轮换 Key 的产品差异化消失。
- 比赛风险：设计与开发总体方案再次分裂，前期收敛成果失效。

#### 推荐

推荐 **方案 A**，不推翻当前产品方向。同时采取两项降风险措施：

1. 设置“官方 NTA 样本验证路径”，真实证明流量解析、Signal、EvidenceReference、只读调查和局部时间线；不得把 SQL 注入或 WebShell 样本改名为云 API Key 滥用。
2. 主 Golden Path 使用明确标识的 Synthetic CI/云事件和 Mock/沙箱状态，并在界面上持续显示数据来源。

【需要比赛方/企业方确认】官方 PCAP 是否为最终必测数据、是否还有深信服平台中的告警/端点/日志数据、擂台赛输入输出接口和评分口径。如果官方要求作品主要解决该 NTA 数据集，当前标杆事件需要重新评审；仅凭现有目录不能擅自确认。

## Step 3：《双文档 + 官方数据三方对齐审查报告》

### P0——开发前必须解决

## Step 6：《为后续开发冻结的设计结论》

### 已确认，可直接进入开发

- 产品保持“面向云服务商安全运营团队的 API 凭据安全事件多智能体协作响应系统”。
- 主标杆事件保持 CI Action 篡改导致 Key 泄露及云侧异常使用。
- 一级角色保持主代理 + 五类受限子代理，不新增 NTA Agent。
- 官方 PCAP 只作为 Official NTA 数据源，不伪装成 CI 或云审计。
- 主 Demo 采用 Official（可用部分）+ Synthetic（缺失业务事件）+ Mock/沙箱（动态动作与状态）。
- LLM 输出不是 Evidence，重要判断必须回指 Raw Event 或确定性系统记录。
- 高风险动作只能经过 ActionRequest、PolicyDecision、人工审批和受控执行。
- 接口 success 不是事件结束，VerificationResult 决定是否进入 VERIFIED/CLOSED。
- 第一阶段只开发一条 Golden Path。

### 待详细设计

- PCAP Raw Event、Flow、EvidenceReference、AgentTask、AgentResult 等 Schema；
- 状态中枢结构、写权限与审计策略；
- 状态迁移表和事件管理器守卫；
- NTA 流量解析与明文协议支持范围；
- Official/Synthetic/Mock 的 source_type、视觉标识和审计字段；
- 规则、工具白名单、Mock 接口和前端交互。

### 待实验验证

- 对 PCAP 的解析完整率、规则检出效果和证据定位稳定性；
- 描述性文件名人工核验后的弱标签可用性；
- SecureBERT2.0 对解析后事件的适用性；
- 共享模型池的结构化输出、时延和资源占用；
- 五分钟 LangGraph 闭环的稳定性。

### 需要 Mock / 沙箱

- API Key 冻结、轮换和恢复；
- 旧 Key/新 Key 状态查询；
- 恶意调用继续或失败的动态结果；
- 合法 CI 使用新 Key 的恢复测试；
- 高费用资源创建停止和资源状态回读。

### 当前不做

- 把 NTA 数据扩张为通用 SOC、SIEM、EDR、IAM 或 CWPP；
- 将全部 2337 个文件直接用于模型训练；
- 未经核验把文件名当 ground truth；
- 跨 PCAP 伪造事件关联；
- 将 Synthetic 说成官方数据，将 Mock 说成生产处置；
- 真实生产凭据、任意 Shell 和无人审批高风险操作。
