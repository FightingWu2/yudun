## 1. 项目定位

御盾智核是一个**「场景化安全智能体」Demo 台**（模块化单体，monolith），不是生产安全产品。它聚焦一条故事线：

> 第三方 **CI Action 被篡改 → CI Runner 访问到 API 凭据 → 凭据被泄露并用于云 API 滥用（敏感读取、高费用资源创建）→ 系统检测、调查、归因、策略判定、人工审批（或沙箱自治预授权）、受控处置、验证、审计关闭**。

P0 里程碑（DEV-001～DEV-030）已完成，核心目标是把这条 **Golden Path** 做成：可启动、可在真实浏览器演示、可连续重放、可自动验收（REST/SSE + Playwright E2E）。

技术栈一览：

| 层 | 技术 | 关键入口 |
|---|---|---|
| 后端 | FastAPI + SQLAlchemy(SQLite) + LangGraph | `backend/app/main.py`, `backend/app/api/routes.py` |
| 编排 | LangGraph StateGraph + SQLite 检查点 | `backend/app/orchestration/golden_path.py` |
| Agent | 受限 Agent 契约 + Tool Registry ACL | `backend/app/agents/runtime.py`, `backend/app/tools/registry.py` |
| 前端 | React 19 + Vite 8 + TypeScript（无路由、无状态库） | `frontend/src/App.tsx`, `frontend/src/api.ts` |
| 验收 | Playwright E2E + pytest + ruff/mypy/prettier | `frontend/e2e/*.spec.ts`, `backend/tests/*` |

> ⚠️ 关键认知：**前端是"业务状态的忠实展示层"，不是业务状态的制造者。** 所有业务状态都由后端（确定性服务 + LangGraph）产生，前端只负责拉取、展示、触发 `reset / start / approval` 三个操作。这条原则贯穿全项目，见第 15 节 Non-Negotiable Rules。

## 2. 当前四个业务工作区

前端 `src/App.tsx` 中定义了 4 个工作区（`type Workspace`）：

| 序号 | 工作区 | 业务含义 | UI 展示什么 |
|---|---|---|---|
| 01 | **Detection & Incident** | 从证据开始：选数据源、重放、看检测信号 | 数据重放台（Official 样本 + Synthetic 场景 + 运行模式）、Incident 概览、Security Signals、Evidence Index |
| 02 | **Evidence & Investigation** | 受限智能体协作调查 | Agent 任务卡片（允许工具/实际调用/Finding）、Confirmed Facts、确定性攻击时间线 |
| 03 | **Response & Verification** | 建议 → 授权 → 执行 → 验证彼此分离 | Recommendation、Policy checks、ActionRequest + digest、Mock 前态、审批按钮（或自治预授权面板）、三步执行、六项验证 |
| 04 | **Audit & Trace** | 可审计的结构化推理轨迹与审计链 | Audit Chain VALID/INVALID、Reasoning Trace 节点、append-only 审计记录 |

页面切换只是前端本地 `useState<Workspace>`，不触发后端请求。**角色**（Local Role 下拉）是全局状态，影响 API 请求头与审批按钮的可见性。

## 5. REST / SSE

所有 API 前缀 `/api/v1`（`frontend/src/api.ts` 中 `const API = "/api/v1"`）。前端统一通过 `api<T>(path, role, init?)` 发送，自动带 `Content-Type: application/json` 与 `X-Demo-Role` 头。

### 5.1 请求头（RBAC 载体）

```
X-Demo-Role: ANALYST | APPROVER | AUDITOR | ADMIN
```

后端 `backend/app/api/auth.py`：缺省为 `ANALYST`；角色非法返回 `PERMISSION_DENIED`（403）。

### 5.2 错误结构

非 2xx 响应体：`{ "code": string, "message": string, "retryable": boolean }`。前端 `api<T>()` 将其转为 `Error("CODE: message")`，显示在页面顶部 error banner。

### 5.3 端点清单（后端 `backend/app/api/routes.py`）

| 方法 | 路径 | 角色限制 | 说明 |
|---|---|---|---|
| GET | `/runtime/status` | 全部 | 运行状态（run/incident/stage/run_mode/model_provider） |
| GET | `/replay/sources` | 全部 | 可选 Official 样本、Synthetic 场景、run_modes（含 enabled） |
| POST | `/replay/reset` | ADMIN | 重置演示（删 `.runtime/business.db` 重建） |
| POST | `/replay/start` | ADMIN | 启动重放；body 见下 |
| GET | `/replay/status` | 全部 | 同 `/runtime/status` |
| GET | `/incidents` | 全部 | Incident 列表 |
| GET | `/incidents/{id}` | 全部 | 单个 Incident（含 blocker/next_stage） |
| GET | `/incidents/{id}/bundle` | 全部 | ★ 前端主数据源，一次拉全量（见 `IncidentBundle`） |
| GET | `/incidents/{id}/signals` | 全部 | Signals |
| GET | `/incidents/{id}/evidence` | 全部 | `{incident_evidence, official_validation_evidence}` |
| GET | `/incidents/{id}/agents` | 全部 | `{tasks, results, findings}` |
| GET | `/incidents/{id}/timeline` | 全部 | 攻击时间线 |
| GET | `/incidents/{id}/actions` | 全部 | recommendations/requests/policies/approvals/preauthorizations/executions + digest |
| GET | `/incidents/{id}/verification` | 全部 | Verification 结果 |
| GET | `/incidents/{id}/reasoning-trace` | 全部 | 结构化推理轨迹 |
| GET | `/incidents/{id}/audit` | ANALYST/AUDITOR/ADMIN | `{chain_valid, records}` |
| GET | `/evidence/{evidence_id}` | 全部 | 单个证据详情（脱敏；SECRET 拒绝） |
| GET | `/actions/{action_request_id}` | 全部 | 单个 ActionRequest 及其 policy/approval/preauth |
| POST | `/approvals` | **APPROVER** | 审批决策；body 见下 |
| GET | `/events` | 全部 | SSE 事件流（0.25s 轮询式） |

`POST /replay/start` body（`backend/app/api/schemas.py`）：

```jsonc
{
  "official_capture_id": "capture_id",   // 必须来自 /replay/sources.official
  "synthetic_scenario_id": "scenario_api_key_compromise_v1",
  "run_mode": "PRODUCTION_GUARDED",      // 或 COMPETITION_AUTONOMOUS
  "force_verification_failure": false,   // 测试用：强制第 N 项验证失败
  "model_failure": false                 // 测试用：模拟模型超时
}
```

`POST /approvals` body：

```jsonc
{
  "action_request_id": "arq_...",
  "decision": "APPROVED",                // 或 REJECTED
  "comment": "通过演示控制台批准",
  "expected_digest": "<ActionRequest 的 SHA-256 digest>",
  "request_id": "ui-approved-<arq>"
}
```

> ⚠️ `expected_digest` 必须与后端计算的 `action_request_digest` 一致，否则 409。前端从 bundle 拿 `request_digest` 回填——**不要**让用户手填或前端自行拼接（防止 Request 篡改）。

### 5.4 SSE 事件

- 连接：`new EventSource("/api/v1/events")`（GET，角色头无法附加到 EventSource，后端默认 ANALYST，SSE 端点允许读角色）。
- 实现是**轮询式**：`backend/app/application/demo.py` 的 `EventFeed` 每 0.25s 把增量事件作为 `event: <type>\ndata: {...}\n\n` 输出（不是真长连接推送）。
- 后端发布的事件类型（`EventFeed.publish`）：`replay.reset`、`signal.created`、`agent.task.created`、`fact.confirmed`、`approval.required`、`approval.decided`、`preauthorization.decided`、`execution.step.updated`、`verification.updated`、`incident.closed`、`replan.created`、`incident.updated`。
- 前端订阅（`App.tsx` 中 `eventTypes`）：`incident.updated`、`approval.required`、`approval.decided`、`execution.step.updated`、`verification.updated`、`incident.closed`、`replan.created`。任何一事件触发都会 `refresh()` 重新拉 `/runtime/status` + `/incidents/{id}/bundle`。

## 6. RBAC（本地演示角色）

| 角色 | 可读 | 可写操作 |
|---|---|---|
| **ADMIN** | 全部读端点 | `POST /replay/reset`、`POST /replay/start` |
| **ANALYST** | 全部读端点（含 audit） | 无 |
| **APPROVER** | 全部读端点 | `POST /approvals` |
| **AUDITOR** | 全部读端点 | 无 |

前端依据角色控制 UI：只有 `role === "APPROVER" && stage === "WAITING_APPROVAL"` 且尚未执行时才显示 Approve/Reject 按钮。角色切换是纯前端本地状态，请求时随头传递。

> ⚠️ 这是**本地 Demo 权限隔离，不是生产 IAM/SSO**。`X-Demo-Role` 是明文 header，任何人可伪造；不要把它当安全边界，它只是"演示时把能点的东西分开"。

## 7. Golden Path（一次完整业务闭环）

后端 LangGraph 状态机（`backend/app/orchestration/golden_path.py`）的节点序列：

```
ingest_event → detect_signal → create_incident → plan_investigation
  → run_investigation → run_trace → evaluate_facts → build_action_plan
  → build_action_request → policy_check
      ├─ PRODUCTION_GUARDED  → wait_for_approval（interrupt，等人类审批）
      └─ COMPETITION_AUTONOMOUS → autonomous_preauthorization
  → execute_action → verify_result
      ├─ PASS → generate_audit → close_incident → END
      └─ FAIL → replan_or_manual（REPLAN，Incident 保持 ROTATED）
```

对应业务语义（先语义后代码，见第 21 节逐步讲解）：

1. **Ingest**：重放官方 PCAP + Synthetic 场景，重置 Mock 状态，生成证据。
2. **Detect**：确定性规则产生 Signal（CI Action 突变）。
3. **Incident**：由 Signal 创建 Incident（NEW → DETECTED）。
4. **Investigate**：Main Agent 规划子任务，Investigation Agent 基于证据输出 Finding；Trace Agent 生成确定性时间线。
5. **Facts**：FactValidator 确定性提升 6 个 Confirmed Fact（ATTRIBUTED）。
6. **Plan & Request**：Operation Agent 依据 Recommendation 生成 3 步 ActionRequest（不执行）。
7. **Policy**：确定性 PolicyEngine 8 项检查 → ALLOW_WITH_APPROVAL / ALLOW_WITH_PREAUTHORIZATION / DENY。
8. **Authorization**：Guarded = 人类 ApprovalRecord；Autonomous = 确定性 PolicyPreAuthorization。
9. **Execute**：SYSTEM_EXECUTOR 在 Mock/Sandbox 执行 3 步（FREEZE → CREATE NEW → UPDATE CI），带幂等、快照、证据收据；CONTAINED → ROTATED。
10. **Verify**：6 项恢复断言，6/6 → VERIFIED；任一失败 → REPLAN（保持 ROTATED）。
11. **Audit & Close**：Audit Agent 校验哈希链 → VERIFIED 且审计链 VALID → CLOSED。

## 8. Guarded / Autonomous 两种运行模式

`RunMode`（`backend/app/domain/enums.py`）有两个值：

| 模式 | 授权方式 | 人工 | 允许资源 | 状态 |
|---|---|---|---|---|
| **PRODUCTION_GUARDED** | Policy → 人类审批 → 受控执行 | 必须 1 个 ApprovalRecord | Mock/Sandbox | 已实现，默认 |
| **COMPETITION_AUTONOMOUS** | Policy → 确定性预授权 → 受控执行 | 必须 0 个 ApprovalRecord | **仅** Synthetic/Mock/Sandbox | 已实现 / SANDBOX ONLY |

- Autonomous 需要环境变量 `COMPETITION_AUTONOMOUS_ENABLED=1`（`DemoRuntime._autonomous_enabled`）。前端 `/replay/sources.run_modes` 里 `enabled` 字段决定下拉框该选项是否可选。
- Autonomous 由 `PolicyPreAuthorizationService` 生成 `PolicyPreAuthorization`（`AUTO_PREAUTHORIZED`/`DENY`），**绝不伪造 ApprovalRecord**（`docs/11` 冻结语义）。Autonomous 运行时 UI 显示 `SANDBOX ONLY · NO PRODUCTION SIDE EFFECT · Human Approval Count = 0`。
- 两种模式共用同一 ActionRequest、SYSTEM_EXECUTOR、MockState、Verification、Audit 和状态机，**没有第二套执行器**。

## 9. 来源语义 OFFICIAL / SYNTHETIC / MOCK / SYSTEM

`SourceType`（`backend/app/domain/enums.py`）是**展示与数据可信度的根**，前端每个数据条目都挂 `source_type`，用不同 Badge 展示。语义不可混淆：

| 来源 | 含义 | 能做什么 / 不能做什么 |
|---|---|---|
| **OFFICIAL** | 比赛官方 PCAP/PCAP-NG 离线证据 | 只证明抓包中真实存在的网络事实，可通过 capture/packet locator 回查；**不**与 Synthetic 宣称天然因果 |
| **SYNTHETIC** | 合成 CI 凭据泄露场景 `scenario_api_key_compromise_v1` | 表达 CI 动作变化、Runner 访问凭据、凭据暴露、云 API 异常、敏感读取、高费用资源创建 |
| **MOCK** | 审批后的凭据冻结/新版本/CI 绑定/攻击状态/资源状态与恢复回读 | 是本地 Mock/Sandbox 动态状态，**不是生产云** |
| **SYSTEM** | 策略、审批、执行、验证、状态迁移、审计记录 | 系统对象，不可被当作业务事件 |

前端 `SourceBadge`（`App.tsx`）直接用 `source_type.toLowerCase()` 生成 class，颜色区分。**禁止**把 Synthetic 标成 Official、Mock 标成 Production（见 Non-Negotiable Rules）。

## 10. Agent 权限（受限 Agent + Tool Registry ACL）

Agent 类型（`backend/app/tools/registry.py`）：

```
MAIN_AGENT / SILENT_MONITOR_AGENT / INVESTIGATION_AGENT / TRACE_AGENT
OPERATION_AGENT / AUDIT_AGENT / SYSTEM_EXECUTOR
```

规则：

1. 每个 AgentTask 声明 `allowed_tools` 与 `allowed_context`；Agent 只能调用 `allowed_tools` 内的工具。
2. 全局 Tool Registry 维护 18 个工具定义，每个工具带 `allowed_agent_types`、`required_permissions`、`risk_level`、`side_effect`。调用前 `ToolRegistry.authorize()` 强校验，通过/拒绝都写审计（`TOOL_ACCESS_GRANTED` / `TOOL_ACCESS_DENIED`）。
3. **只有 SYSTEM_EXECUTOR 拥有 `execute_mock_action_plan`**（`CONTROLLED_EXECUTION` 风险级）。OPERATION_AGENT 只能 `create_action_request`（`PROPOSAL_ONLY`），**不能执行**。
4. Investigation/Trace/Operation Agent 的 `allowed_tools` 里**显式没有执行类工具**——前端 Investigation 页把 `execute_mock_action_plan` 固定显示在 "Explicitly denied" 区。
5. Main Agent 创建子任务时不能扩大 evidence/fact 范围（`AgentRuntime.create_planned_task` 校验越界即 `PERMISSION_DENIED`）。

前端只读展示：Agent 卡片显示 allowed tools / actual calls / findings；**绝不让 Agent 看起来拥有执行权**（Non-Negotiable Rule）。

## 11. Finding / Fact 区别

| | **Finding**（Agent 输出） | **Fact**（ConfirmedFact） |
|---|---|---|
| 产生者 | Investigation/Trace Agent 的模型输出或确定性构造 | `FactValidator.promote()` 确定性提升 |
| 依据 | 结构化模型输出 + evidence refs | 必须引用证据、且 6 个 Golden Path fact 全齐才提升 |
| 可信度 | `confidence_level`（LOW/MEDIUM/HIGH），可带 `limitations` | 已验证事实，`validated_by` 记录验证者 |
| 展示 | Investigation 页 Agent 卡片内 | Investigation 页 "Finding → Fact" 区 |

- UI 反复强调：**Signal ≠ ConfirmedFact**；**Finding 必须经过验证才能成为 Fact**。
- 前端 `bundle.facts` 只渲染 `ConfirmedFact` 列表，`bundle.findings` 渲染在 Agent 卡片内。**禁止把 Finding 直接当 Fact 展示**（Non-Negotiable Rule）。

## 12. Policy / Approval / Execution / Verification 边界

这是最容易越界的四条线，前端展示必须严格区分：

| 对象 | 产生者 | 作用 | 关键约束 |
|---|---|---|---|
| **PolicyDecision** | `PolicyEngine`（确定性，非 LLM） | 判定 ActionRequest 是否被允许 | 8 项检查；`ALLOW_WITH_APPROVAL` / `ALLOW_WITH_PREAUTHORIZATION` / `DENY` |
| **ApprovalRecord** | 人类（APPROVER 角色） | 记录人类对 Request 的批准/拒绝 | 校验 digest；**审批只恢复 LangGraph**，不直接改状态 |
| **PolicyPreAuthorization** | `PolicyPreAuthorizationService`（确定性） | Autonomous 沙箱预授权 | `AUTO_PREAUTHORIZED`/`DENY`；不是 ApprovalRecord，ApprovalRecord 数必须为 0 |
| **ExecutionResult** | `ControlledExecutor`（SYSTEM_EXECUTOR） | 真正改变 Mock/Sandbox 状态 | 需 Policy+Approval（Guarded）或 Policy+Preauth（Autonomous）+ digest；幂等；快照/收据/证据 |
| **VerificationResult** | `VerificationEngine`（确定性） | 6 项恢复断言决定是否 VERIFIED | 6/6 → `next_step=CLOSE`；任一失败 → `REPLAN` |

四条边界（也写进 UI 文案）：

1. **Policy 不是 LLM 决定**——PolicyEngine 是确定性代码。
2. **Approval / PreAuthorization ≠ Execution**——批准只恢复工作流，不改变状态；只有 Execution 改变 Mock。
3. **Execution Success ≠ Incident Resolved**——执行成功只到 ROTATED，必须验证 6/6 才 VERIFIED。
4. **Verification 和 Audit 决定最终关闭**——VERIFIED + 审计链 VALID 才 CLOSED。

## 13. Reasoning Trace（可审计结构化推理轨迹）

- 后端 `ReasoningTraceService`（`backend/app/audit/reporting.py`）从审计记录构建结构化节点，阶段映射：

```
Observation → Evidence → Task → Finding → Fact → Decision → Action → Observation → Replan
```

- 每个节点只包含：`timestamp`、`stage`、`actor`、`object_type`、`object_id`、`summary`、`input_refs`、`output_refs`、`source_type`（=SYSTEM）、`result`。
- **不保存、不展示模型私有隐藏推理（隐藏 CoT）**。Audit 页文案明确："展示 Observation、Evidence、Task、Finding、Fact 与 Decision，不展示隐藏 CoT。"
- 前端 `bundle.reasoning_trace` 渲染在 Audit 工作区，每条是一个结构化节点卡片。
- 该轨迹是**展示层重构的产物**，不是模型原样输出——结论必须回指 Evidence。

## 15. Frontend Non-Negotiable Rules（前端不可协商规则）

> 这些规则是**项目验收红线**，任何前端改动（包括"看起来更合理的 UI"）都不得违反。违反了 = 后端安全失败回归（`security-failures.spec.ts` / E2E）会失败，甚至误导裁判与演示。

1. **UI 不能制造业务状态**。前端只读后端返回的状态，不 setState 伪造（例如不能本地把 `status` 改成 `CLOSED`）。所有 `bundle` 字段都来自 `/incidents/{id}/bundle`。
2. **Synthetic 不能显示为 Official**。来源 Badge 必须严格绑定 `source_type` 字段。
3. **Mock 不能显示为 Production**。Mock/Sandbox 状态必须标注"本地沙箱"，不得显示成真实云。
4. **Finding 不能显示为 Fact**。Finding 与 ConfirmedFact 分区展示，措辞保留"Finding → Fact / 需验证"。
5. **Agent 不能显示成拥有执行权**。只有 SYSTEM_EXECUTOR 能执行；Agent 卡片保留 allowed/denied 工具区。
6. **Policy 不是 LLM 决定**。Policy 面板是确定性检查结果，文案/图标不得暗示"模型决定策略"。
7. **Approval / PreAuthorization 不等于 Execution**。批准只恢复工作流；Mock 前态在批准前必须未变。
8. **Execution Success 不等于 Incident Resolved**。执行后 Incident 是 ROTATED，必须展示"仍需验证"。
9. **Verification 和 Audit 决定最终关闭**。只有 `VERIFIED` + 审计链 `VALID` 才 CLOSED；UI 不能在验证/审计通过前显示关闭。
10. **不能展示或伪造隐藏 CoT**。只展示结构化 Reasoning Trace；不渲染任何"模型思考过程"原文。
11. **实际模型 Provider 必须真实显示**。MODEL 字段绑定后端返回的 provider 字符串。

附带铁律：**不能绕过 RBAC 伪造角色**；**不能绕过 `expected_digest` 校验**；**不能删除/重命名 e2e 依赖的 `data-testid` 或文案**（否则 `make demo-e2e` 失败，除非同步改 spec）。

## 18. 已知问题（接手时心里有数）

1. **App.tsx 是 1088 行单文件**，无路由/状态库，是最大可维护性技术债；重构是允许的（见第 16 节）。
2. **前端依赖用 `"latest"`**：`package-lock.json` 锁定当前（vite 8.2.1 / react 19.2.8 / ts 6.0.3），但新人重装时容易漂移；建议固定版本。
3. **跨平台二进制**：`node_modules` 含 macOS 原生二进制（rolldown/vite 8），在 Linux/CI 上**不能直接用**，必须重新 `npm ci`。
4. **SSE 是 0.25s 轮询**，不是真推送；高频刷新下网络开销小但实时性一般。
5. **`X-Demo-Role` 是明文 header**，仅本地演示；无登录/多租户。
6. **`data/`（257MB PCAP）不入 git**；新环境需要从原始数据集恢复，否则 `start` 会因找不到 capture 报 `SOURCE_UNAVAILABLE`。
7. **`frontend/dist/` 不入 git**；`make contest-preflight` 依赖 `dist/index.html`，新机器先 `npm run build`。
8. **E2E 需要 Playwright Chromium**：macOS 与 Linux 安装命令不同；无网络环境无法安装。
9. 后端 `business.db` 位于 `.runtime/`，每次 `reset` 删除重建；`checkpoints.db` 存 LangGraph 检查点，`reset` 也会清。
10. 深信服平台接入、Security Knowledge RAG、真实模型 live 验证均**未完成**，不要把未完成能力画进 UI 或文案。
11. `frontend/tests/` 为空目录；Playwright 测试在 `e2e/`。
12. 容器/VM 中无法运行完整回归（Python 3.11 与原生二进制受限）；权威回归以宿主机为准（见第 19 节）。

## 20. 完整演示：Reset → Replay → Evidence → Agent → Fact → Timeline → Policy → Autonomous/Guarded → Execution → Verification → Audit → CLOSED

> 先讲**业务语义**，再讲**代码入口**。以 `make demo-e2e` 的浏览器路径为脚本（对应 `frontend/e2e/golden-path.spec.ts`）。

### Step 0 · Reset（重置）
- **业务语义**：清空上一轮一切业务对象，回到 IDLE，准备全新一轮。绝不混入上一轮 Incident/Run。
- **代码**：前端 `App.tsx` `reset()` → `POST /replay/reset`（ADMIN）→ `DemoRuntime.reset()`（`backend/app/application/demo.py`）删除 `.runtime/business.db*`、`checkpoints.db*` 重建，`EventFeed.clear()`，发布 `replay.reset`。

### Step 1 · Replay（选源并重放）
- **业务语义**：ADMIN 从明确标识的数据源里选一个 Official NTA 样本 + 一个 Synthetic 场景，再选运行模式，开始重放。Official 与 Synthetic **不宣称天然因果**。
- **代码**：`DetectionWorkspace` 渲染 `sources.official[]` 与 `sources.synthetic[]` 下拉 + run_mode 下拉（来自 `GET /replay/sources`）。`start()` → `POST /replay/start` → `DemoRuntime.start()` 校验 scenario allowlist、导入 Official 证据、构造 `GoldenPathWorkflow` 并 `invoke`。

### Step 2 · Evidence（证据）
- **业务语义**：证据是结论的根。Official 证据来自官方抓包（locator 可回查）；Synthetic 证据来自场景。Signal 由规则从证据产生，Signal ≠ Fact。
- **代码**：`DetectionWorkspace` 的 Evidence Index（`bundle.evidence` + `bundle.official_evidence`）与 drawer（`GET /evidence/{id}`）展示 `redacted_snapshot`（脱敏）与 `locator`。

### Step 3 · Agent（受限智能体）
- **业务语义**：Agent 只能在它被授权的证据范围与工具集内活动；Investigation Agent 输出 Finding；Trace Agent 构建时间线。Agent 不能执行。
- **代码**：`InvestigationWorkspace` 遍历 `bundle.tasks`，对每个任务显示 allowed tools、实际调用（从 `bundle.audit.records` 过滤 `TOOL_ACCESS_GRANTED` 且 `actor_id == assigned_agent_type`）、Findings。

### Step 4 · Fact（确定性命中事实）
- **业务语义**：只有经 `FactValidator` 确定性验证的才是 Confirmed Fact；Golden Path 恰好 6 个（CI 突变、凭据被访问、暴露、滥用、敏感读取、高费用资源创建）。6/6 才 ATTRIBUTED。
- **代码**：`bundle.facts` 渲染在 "Finding → Fact" 区；`evaluate_facts` 节点逐个 `promote()`，`FactValidator` 必须见证据才提升。

### Step 5 · Timeline（确定性时间线）
- **业务语义**：时间线节点来自证据的精确时间字段并按时间排序；来源混排时明确声明 missing links（不伪造跨源因果）。
- **代码**：`timeline` 由 `bundle.findings` 中 `finding_type === "ATTACK_TIMELINE"` 的 `metadata.timeline.nodes` 计算（`App.tsx` `useMemo`）。时间线节点可点 "View Evidence" 打开 drawer。

### Step 6 · Policy（策略判定）
- **业务语义**：PolicyEngine 确定性判定请求是否允许、需要人审还是预授权。这是规则，不是模型结论。
- **代码**：`ResponseWorkspace` 渲染 `bundle.actions.policies.at(-1)` 的 8 项 `checks`（✓/×）与 `decision`。

### Step 7 · Autonomous / Guarded（授权分支）
- **业务语义**：Guarded 必须人类 APPROVER 核对 digest 后批准；Autonomous 由确定性预授权放行且 ApprovalRecord 必须为 0。批准只恢复工作流。
- **代码**：Guarded：`bundle.actions.approvals` / 审批按钮（`role==='APPROVER' && stage==='WAITING_APPROVAL' && !execution`）→ `decide()` → `POST /approvals`（带 `expected_digest`）。Autonomous：`bundle.actions.preauthorizations.at(-1)` → `PreAuthorizationPanel`（`AUTO_PREAUTHORIZED` + guard checks）。两者在 `wait_for_approval`（LangGraph `interrupt`）或 `autonomous_preauthorization` 节点落地。

### Step 8 · Execution（受控执行）
- **业务语义**：只有 SYSTEM_EXECUTOR 能改变 Mock/Sandbox 状态，顺序固定 `FREEZE_OLD_KEY → CREATE_NEW_KEY_VERSION → UPDATE_CI_BINDING`，幂等 + 快照 + 证据收据；Incident 从 CONTAINED 到 ROTATED。
- **代码**：`ResponseWorkspace` 渲染 `bundle.actions.executions.at(-1)` 的 `operation_results`（Before/After snapshot + receipt）；`ControlledExecutor`（`backend/app/actions/service.py`）在 `execute_action` 节点执行。

### Step 9 · Verification（恢复验证）
- **业务语义**：6 项恢复断言（旧 key 禁用、旧 key 调用被拒、恶意活动停止、新 key 激活、CI 恢复、高费用资源停止）。6/6 → VERIFIED；任一失败 → REPLAN，Incident 保持 ROTATED。
- **代码**：`ResponseWorkspace` 渲染 `bundle.verification.at(-1)` 的 `assertions`（✓/×、observed/expected）；失败时展示 error banner 与 `next_step === "REPLAN"`。

### Step 10 · Audit（审计）
- **业务语义**：审计链是 append-only + SHA-256 哈希链；VALID 才是可信的关闭前提。
- **代码**：`AuditWorkspace` 渲染 `bundle.audit.chain_valid`（VALID/INVALID）与 `bundle.audit.records`（倒序）。

### Step 11 · CLOSED（关闭）
- **业务语义**：只有 VERIFIED + 审计链 VALID + 无遗留高危动作才 CLOSED。前端顶栏 STATUS 显示 CLOSED，SSE 发布 `incident.closed`。
- **代码**：`close_incident` 节点 → `IncidentClosureService.close()` → `EventStateManager` 迁移到 CLOSED；E2E 断言 `global-state` 含 CLOSED。

> 全流程的**一次性数据视图**是 `GET /incidents/{id}/bundle`（`IncidentBundle`），前端所有工作区都从同一个 bundle 取数，SSE 事件触发重新拉取。因此前端永远不需要自行维护跨页面状态。
