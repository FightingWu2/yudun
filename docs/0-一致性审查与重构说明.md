# 《1-设计文档》×《2-开发-总体方案》一致性审查与重构说明

> 审查基准：以 `2-开发-总体方案.md` 中已确认内容为当前事实基准。  
> 审查目的：使产品设计回答“为什么做、为谁做、做什么、如何工作”，使开发方案回答“具体怎么实现”。

## 第一部分：总体判断

### 1. 整体是否一致

两份文档在“多源证据关联、有界自治、最小权限、高风险审批、执行后验证、全链路审计”等原则上方向一致，但在当前产品究竟服务谁、重点处理什么事件、由哪些 Agent 完成、Demo 证明什么等关键事实上并不一致。旧设计更接近面向政企 SOC 的通用安全运营平台，最新开发方案已经收敛为面向云服务商安全运营团队的 API 凭据泄露与滥用响应系统。

### 2. 最大冲突

1. **客户与产品范围冲突**：旧设计面向公安、金融、医疗、教育、能源等政企 SOC；最新方案的直接客户和使用者是云服务商安全运营团队，租户及其业务是最终受保护对象。
2. **标杆事件冲突**：旧设计以“失陷身份—端点—横向移动”为主线；最新 Demo 是“第三方 CI Action 篡改—API Key 泄露—异常云 API 调用—数据读取与高费用资源创建”。
3. **Agent 架构冲突**：旧设计按安全产品域划分身份、API、端点等 Agent；最新方案按安全工作阶段和权限边界划分静默监测、事件调查、攻击溯源、操作执行、审计汇报子代理，并由主代理统一调度。
4. **治理能力成熟度冲突**：旧设计把 Agent PKI、MCP Server 签名、完整熔断中心等写成当前能力；最新方案当前确认的是固定工具权限、禁止自由通信、明文凭据隔离、策略校验、人工审批、状态中枢和审计。
5. **Demo 与实现边界冲突**：旧设计安排四类演示并覆盖 EDR、横向移动、提示注入等能力；最新阶段只要求一个云平台、一个租户事件模型、一类 API Key 和一条可在五分钟内闭环的攻击链。

### 3. 为什么必须修改

如果不修改，评委会看到“设计文档承诺通用政企 SOC 和完整智能体治理平台，开发现场却只展示云侧 API Key 事件”，从而质疑产品定位、创新点真实性和团队的工程判断。开发人员也会因一级 Agent、数据源、动作对象和验收范围不一致而无法据文档拆解任务。

### 4. 总体重构策略

- 以云服务商安全运营团队为当前直接用户，以租户 CI/CD 与云 API 凭据事件为 Demo 主线。
- 保留“证据协作、有界自治、最小权限、模型与授权解耦、执行后验证、全链路审计”等优秀思想，并映射到已确认架构。
- 将未进入当前开发范围的行业泛化、端点响应、完整 Agent 身份体系和 MCP 供应链治理明确降为后续扩展。
- 在设计文档中用【已确认】【待验证】【待设计】【建议】区分成熟度，避免把设计意图写成实现事实。

## 第三部分：新的产品逻辑

### 产品是什么

“御盾智核”是面向云服务商的 API 凭据安全事件多智能体协作响应系统，连接租户授权的 CI 安全事件与云侧日志，完成监测、调查、溯源、受控处置、恢复验证和审计汇报。

### 谁使用

直接客户和主要使用者是云服务商安全运营团队；云租户提供授权数据并参与高风险审批，其 API 凭据、云资源、敏感数据和业务连续性是最终受保护对象。

### 解决什么问题

系统解决 API Key “可能暴露”与“已经被利用并造成影响”难以区分的问题，把 CI 组件异常、云 API 调用、认证流量、资源操作和凭据状态关联为可验证事件，并缩短从发现到止损、恢复的链路。

### 为什么需要多智能体

多智能体首先是一种安全边界：监测、调查、溯源、操作申请和审计分别拥有不同数据与工具权限，任何单一模型都不能同时看见全部敏感数据并控制生产动作。其次，不同任务可匹配分类、检索、整理与编排模型，降低成本并提高结果可审计性。

### 标杆事件是什么

标杆事件为“第三方 CI Action 篡改引发的 API Key 泄露与云资源滥用事件”：被篡改组件从 Runner 读取并外传 Key，攻击者随后读取敏感数据并创建高费用资源。

### 系统如何解决

静默监测子代理生成结构化告警，主代理基于事件状态调度调查与溯源；处置建议经操作执行子代理格式化后，由确定性策略和人工审批放行，再通过受控接口冻结/轮换并回读验证，最后形成审计报告。

### 产品最大差异化

差异化不在“用了多个模型”，而在把多智能体分工转化为数据、职责、权限和风险隔离，并以事件状态中枢、确定性策略、人工审批和执行后验证组成可证明的有界自治闭环。

8. **多智能体体系**：冻结主代理、五类子代理和权限边界。

## 第六部分：反向检查

### 当前最强的 3 个点

1. **场景与闭环高度一致**：CI 供应链异常能够解释 Key 从何泄露，云侧调用能够证明 Key 是否被利用，冻结/轮换/恢复验证能够证明系统是否真正止损。
2. **多智能体是安全边界而非数量包装**：只读调查与有副作用操作隔离，工具权限固定，子代理禁止自由通信，高风险动作不由模型授权。
3. **模型判断与确定性控制解耦**：模型负责分类、检索、整理和建议，策略与人工负责放行，事件状态与审计记录负责可追溯。

### 当前最容易被评委质疑的 3 个点

1. CI Action 异常与云 API 异常的关联规则、时间窗和误报控制尚未冻结，若只用预置剧情会被质疑为“串日志”。
2. LangGraph、事件状态中枢、审批暂停恢复和受控执行目前仍待开发，若前端仅播放固定动画，无法证明真实编排。
3. SecureBERT2.0、Qwen3-4B、BGE-M3 与接口大模型的角色分工合理，但真实效果、中文适配、时延和资源占用尚无测试数据。

### 开发阶段必须证明的 5 个关键能力

1. 两条独立信号进入系统后，能够以稳定、可解释的规则关联到同一事件，并保留原始证据引用。
2. 主代理能依据事件状态真实选择并调度子代理，子代理获得的上下文和工具权限符合最小必要原则。
3. 调查与溯源能输出结构化结论、证据、未决项和下一步，而非只有自然语言分析。
4. 冻结、轮换等高风险请求能够被确定性策略拦截并暂停等待人工审批，模型和主代理无法绕过。
5. 受控执行后能回读旧 Key、新 Key、恶意调用和合法业务状态，并据此决定关闭事件或继续调查。

### 只能写“规划中”的能力

- 完整 Agent PKI、Agent 凭证生命周期和跨组织身份体系。
- MCP Server 签名、完整工具供应链准入与大规模工具市场治理。
