- **【需要比赛方/企业方确认】**：仅靠现有文档和数据无法确定，必须从比赛平台、发榜单位或企业接口方获得答案。

除明确标注为【建议】【待验证】【待设计】的内容外，本文对当前产品定位、业务流程和边界的描述均按已确认方案编写。“系统完成某项工作”表示目标产品流程，不等同于该能力当前已经编码完成；实现状态以开发验收记录为准。

## 2. 产品总体定义

### 2.1 产品名称

> **御盾智核**

### 2.2 一句话定位

> **御盾智核是面向云服务商安全运营团队的 API 凭据安全事件多智能体协作响应系统，通过职责、数据和操作权限隔离，协同完成异常监测、事件调查、攻击溯源、受控处置、恢复验证与审计汇报。**

### 2.3 产品解决的核心问题

API Key 可能从公开代码、容器镜像、CI/CD 环境或第三方自动化组件中泄露，但“可能暴露”不等于“已经被攻击者利用”。安全运营团队必须进一步回答：Key 是否仍有效、是否出现异常调用、读取了什么数据、创建了什么资源、造成了什么影响，以及如何在不扩大业务损失的前提下完成止损和恢复。

御盾智核将租户授权的 CI 安全事件与云侧 API、认证流量、资源操作和凭据状态证据关联到同一安全事件，使调查、决策、审批、执行和验证围绕统一事实推进。

### 2.4 产品不是什么

御盾智核不是：

- 通用安全聊天机器人；
- 替代云审计、IAM、SIEM、EDR 或其他安全设备的新探针；
- 允许大模型直接修改生产资源的自动执行器；
- 当前已经覆盖所有云平台、凭据类型和安全事件的通用 SOC 平台；
- 以“多个 Agent 互相聊天”为核心的演示系统。

它是连接既有数据源和受控安全能力的事件协作与响应中枢。

### 2.5 工作原则

> **证据驱动判断，状态驱动协作，权限限制能力，策略约束动作，回读验证结果，审计贯穿全程。**

## 3. 现实问题与产品价值

### 3.1 凭据暴露与实际滥用之间存在事实断层

发现 CI 组件异常或 Secret 访问行为，只能说明凭据存在暴露可能；发现一次陌生来源调用，也不能单独证明攻击成功。安全人员需要继续核对凭据有效性、历史用途、来源变化、调用频率、敏感接口访问和资源操作，才能判断事件性质与影响。

产品价值：把“风险线索”逐步推进为“有证据支持的事件事实”，避免因单条告警直接冻结凭据，也避免在已发生滥用时迟迟不能止损。

### 3.2 CI 与云侧证据分散，攻击链难以还原

泄露起点发生在租户 CI/CD 环境，实际损害发生在云 API 和云资源侧。两部分通常属于不同日志域，安全人员需要手工关联 Action 版本或 Digest、Runner、Secret 访问、API Key 标识、调用来源、数据读取和资源创建记录。

产品价值：以事件 ID、时间线、实体引用和证据位置组织跨域事实，解释“Key 从哪里泄露、由谁在何处使用、造成了什么影响”。

### 3.3 人工调查链路长，攻击动作却可以快速自动化

传统流程需要人员在多个系统间查询、复制、比对、申请和回读。重复查询占用时间，高风险判断又不能省略。

产品价值：让受限子代理承担分类、检索、证据整理和报告生成，让安全运营人员聚焦证据审核、例外判断和高风险审批。

### 3.4 模型判断不能直接等同于操作授权

冻结或轮换 API Key 可能中断租户发布、数据处理和生产任务。模型可能误判，也可能受不可信日志、工具返回或提示注入影响。

产品价值：调查代理与操作代理权限隔离，模型只生成建议或结构化申请；确定性策略检查前置条件，生产高风险操作由人工审批，最终由受控接口执行。

### 3.5 接口返回成功不等于安全事件已经解决

凭据冻结成功后仍需确认旧 Key 确实失效、异常调用停止；轮换后还需确认新 Key 可用、合法业务恢复。只记录一次成功响应会把“动作完成”误当成“风险消除”。

产品价值：把状态回读和恢复验证作为事件关闭的必要条件，使闭环结果可被演示、复核和审计。

### 3.6 现实依据

当前开发方案已列出公开依据，包括 GitGuardian secrets sprawl 报告、Verizon DBIR、GitHub Secret Scanning、Codecov 与 CircleCI 事件说明、AWS IAM Access Key 处置建议。本文仅据此说明场景具有现实基础；正式项目书引用时应再次核验版本、发布日期和原始链接。

## 4. 用户、服务关系与使用场景

### 4.1 直接客户

【已确认】直接客户是需要建设或增强租户安全运营能力的云服务商。

### 4.2 直接使用者

【已确认】主要使用者是云服务商安全运营团队，包括值班分析人员、事件调查人员、响应审批人员和安全运营负责人。不同人员通过角色权限查看事件、补充证据、审批动作或查阅报告。

### 4.3 协作参与方

云租户在授权范围内提供 CI 安全事件和必要上下文，并可参与涉及自身业务的高风险审批、凭据轮换和恢复确认。系统不假设云服务商可以无条件读取租户 CI 内部数据。

### 4.4 最终受保护对象

- 租户 API 凭据及其授权边界；
- 租户敏感数据；
- 租户云资源和费用；
- 租户 CI/CD 与依赖该凭据的合法业务连续性。

### 4.5 可扩展市场

【后续扩展】该架构未来可适配托管安全服务团队、大型企业云安全中心，以及金融、医疗、教育、能源等行业的云上凭据事件。上述行业不是本阶段已实现范围，不能在比赛中表述为已有行业落地。

## 5. 官方比赛数据与产品关系

### 5.1 比赛方到底提供了什么

【数据事实】`data/测评中心基线样本nta/` 包含 2337 个 PCAP/PCAP-NG 网络抓包文件，总计约 257 MB。PCAP 可以理解成网络通信录像，记录包时间、通信 IP、端口、协议，以及未加密流量中的 HTTP、DNS、数据库等请求或响应内容。

目录中没有 README、字段说明、结构化标签表、CSV、JSON、JSONL、CI 事件、云 API 审计、凭据状态或云资源费用数据。文件名中的 `.json.pcap` 仍是二进制抓包，不是 JSON。

主要数据特征：

- 2336 个经典 PCAP、1 个 PCAP-NG；
- 约 708,924 个网络包；
- 每个文件包数中位数为 7，说明多数是短攻击片段，不是完整企业安全事件；
- 主要为 2020—2021 年流量，也包含 2007—2023 年其他样本；
- 描述性文件名涉及 SQL 注入、RCE、WebShell、命令执行、DNSLog、隧道、弱口令等 NTA 攻击行为；
- 719 个描述性文件名只能作为弱标签线索，1618 个不透明 ID 文件名不能说明类别；
- 没有明确 normal/benign 组和 ground truth，不能直接作为完整监督学习训练集或计算可信整体误报率。

完整盘点和样例验证见 `3-官方数据集理解与三方对齐报告.md`。

### 5.2 官方数据真实能够支持什么

| 能力 | 支持程度 | 真实依据 |
|---|---|---|
| 网络流量接入和离线重放 | 完全支持 | PCAP/PCAP-NG 原始抓包 |
| 提取时间、IP、端口和协议 | 完全支持 | Ethernet、IPv4、TCP/UDP/ICMP 等包头 |
| 识别部分恶意 HTTP/DNS/数据库行为 | 支持 | 明文方法、URI、参数、Host、DNS 查询和部分响应可见 |
| 同一抓包内形成网络时间线 | 支持 | 时间戳 + 五元组 + TCP 序列/请求响应 |
| 跨抓包关联为同一安全事件 | 不支持 | 没有统一 incident_id/trace_id，实验 IP 被重复使用 |
| 证明 CI Action、Runner 或 Secret 访问 | 不支持 | 没有 CI/CD 结构化事件 |
| 证明某个 API Key 被使用 | 不支持 | 没有稳定 credential_id；少量认证字符串不等于本项目 Key |
| 证明云资源创建、费用或权限影响 | 不支持 | 没有云审计和资源状态字段 |
| 动态冻结、轮换与恢复验证 | 不支持 | PCAP 是离线历史数据，不具备可变业务状态 |

### 5.3 官方数据与当前产品的匹配判断

结论是：**部分匹配，主标杆攻击链存在结构性数据缺口。**

交集包括网络侧异常发现、局部调查、同一 PCAP 内时间线和 EvidenceReference 回查；缺口包括 CI Action、Runner、Credential ID、云 API 身份、租户资源、高费用操作和动态凭据状态。

本基线不因数据集改造成通用 NTA/SOC 产品。推荐保持 API 凭据事件定位，并采用三种明确区分的数据来源：

1. **Official**：官方 PCAP，用于验证流量解析、网络 Signal、EvidenceReference、只读调查和局部时间线；
2. **Synthetic**：团队构造且明确标识的 CI、云 API、凭据标识和资源事件，只补齐官方数据缺失的业务环节；
3. **Mock/Sandbox**：维护冻结、轮换、恢复和执行回读的动态状态。

不得把 SQL 注入或 WebShell PCAP 改名为 API Key 滥用，不得把 Synthetic 事件说成官方数据，也不得把 Mock 状态说成生产云处置。

### 5.4 当前数据使用决策

- 主 Golden Path 仍然围绕 CI Action—API Key—云侧滥用展开；
- 官方 PCAP 作为独立的“官方 NTA 样本验证路径”，证明静默监测、证据引用和网络侧调查能力；
- 若主 Demo 引用某个官方 PCAP，界面必须分别展示“官方原始网络证据”和“合成的跨域关联元数据”，不能暗示关联键来自官方；
- 首版不直接训练模型，先建立解析能力、人工核验样本子集和可解释规则；
- 【需要比赛方/企业方确认】官方 PCAP 是否为最终必测数据、深信服平台是否还提供告警/端点/日志数据、擂台赛接口和评分口径。若官方要求作品主要解决该 NTA 数据集，标杆事件需重新评审。

## 6. 标杆安全事件

### 6.1 事件名称

> **CI 供应链篡改引发的 API Key 泄露与云资源滥用事件**

该名称同时交代攻击入口、关键资产和云侧后果，非安全专业评委也能理解基本因果关系。

### 6.2 攻击链

```text
第三方 CI Action 被篡改
    → CI Runner 执行异常组件
    → 组件读取环境变量中的 API Key
    → API Key 被外传
    → 攻击者从异常来源调用云 API
    → 读取租户敏感数据
    → 创建高费用云资源
    → 系统调查、溯源并形成处置建议
    → 策略校验与人工审批
    → 冻结 / 轮换凭据
    → 验证旧 Key 失效、新 Key 可用、合法业务恢复
    → 形成审计报告
```

### 6.3 攻击链数据覆盖

| 攻击链节点 | 官方数据覆盖 | 当前产品数据来源 | 真实性边界 |
|---|---|---|---|
| CI Action 被篡改 | 不支持 | Synthetic CI Security Event | 明确显示 `source_type=SYNTHETIC` |
| Runner 读取 Key | 不支持 | Synthetic Secret Access Event | 只使用 Key 指纹/标识，不生成明文 Key |
| Key 泄露 | 不支持 | Synthetic Exfiltration Event | 作为演示事实，不声称来自官方 PCAP |
| 异常调用云 API | 部分支持网络请求，不支持 Key/云身份 | Synthetic Cloud Audit；可附 Official PCAP 网络证据 | 两类证据分别标识，不能伪造 credential_id |
| 敏感数据读取 | 部分 PCAP 有数据库/HTTP行为，但不证明云租户数据 | Synthetic Resource Access Event；Official 仅用于其真实流量案例 | 结论必须回指对应来源 |
| 高费用资源创建 | 不支持 | Synthetic Resource Operation + Mock Resource State | 费用与资源字段不得声称来自官方 |
| 冻结、轮换、恢复 | 不支持 | Mock/沙箱状态服务 | 只宣称演示环境受控执行 |
| 调查、审批、审计 | 运行时生成 | 系统事件状态与审计记录 | 可证明系统流程，不代表生产部署 |

### 6.4 事件起点

【已确认】目标产品接收两条可独立出现的信号：

1. 租户 CI 安全连接器发现第三方 Action 的版本、Digest、权限或 Secret 访问行为异常；
2. 云侧监测发现相关 API Key 出现异常调用。

任一高风险信号出现时创建安全事件并进入“已发现”状态。两条证据能够关联时，事件升级为高风险并进入完整调查流程。

当前官方数据不包含上述两类结构化事件，因此比赛主 Demo 通过 Synthetic 事件重放实现，并持续显示来源标签。两条信号的具体关联字段、时间窗、证据数量和升级阈值【待设计】；Demo 可以使用确定性样例规则，但必须公开规则口径，不能把预置关联描述为模型自主发现。

### 6.5 为什么选择这条攻击链

1. **现实问题明确**：第三方自动化组件、CI Secret 与云 API Key 构成真实供应链风险面。
2. **证据跨域但边界可控**：既能展示 CI 与云侧多源关联，又不需要搭建完整 SIEM、EDR 和企业网络。
3. **多智能体必要性可证明**：监测、调查、溯源、操作和审计在数据与权限上天然不同。
4. **处置结果可验证**：旧 Key 是否失效、异常调用是否停止、新 Key 是否可用都能通过 Mock 或沙箱回读。
5. **五分钟可讲清**：起因、滥用、影响、审批、止损和恢复形成单一因果链。

选择单一标杆事件不是放弃通用性，而是先用一条完整链路验证通用角色、事件状态和受控执行机制。比赛阶段不泛化展示所有安全事件。

## 7. 产品核心能力

### 7.1 多源信号接入与事件创建

通过安全连接器接收租户授权的 CI 事件、云 API 审计、流量与认证、资源操作和凭据状态数据。系统对输入进行标准化、脱敏和证据引用，原始明文 API Key 不进入模型上下文或普通日志。

### 7.2 静默监测与可解释告警

静默监测子代理在后台对只读事件进行分类和初筛，输出风险信号、关联对象、证据引用和触发原因。告警不是最终定性，只是启动或升级事件的依据。

### 7.3 事件调查与影响确认

事件调查子代理围绕告警查询必要证据，回答 Key 是否被异常使用、敏感数据是否被读取、高费用资源是否被创建，以及当前损害是否仍在持续。

### 7.4 攻击溯源与时间线还原

攻击溯源子代理关联 Action、Runner、Key 标识、来源 IP/地区/设备、API 调用和资源操作，形成有证据引用的时间线。溯源结论用于还原技术路径，不凭模型输出认定现实攻击者或组织。

### 7.5 状态驱动的协作编排

主代理读取事件当前状态、已确认事实和未决问题，按任务依赖关系串行或并行调用只读子代理。重复调用必须带有新的调查目标；连续调用未产生新证据时，应停止并报告证据不足。

### 7.6 受控响应

主代理形成处置计划，操作执行子代理只把建议转换为固定格式申请。确定性策略检查动作类型、对象、前置条件和审批要求；人工批准后，受控接口才可在 Mock 或沙箱环境中执行冻结、轮换、恢复或查询。

### 7.7 恢复验证与事件关闭

系统回读旧 Key、新 Key、恶意调用和合法业务状态。只有达到验证条件，事件才能从“已遏制/已轮换”推进为“已验证/已关闭”；否则返回调查或处置环节。

### 7.8 审计汇报

系统保留告警、调度、证据、结论、状态变更、操作申请、策略结果、审批和执行回读。审计汇报子代理基于这些记录生成脱敏报告，但不能修改或删除底层审计事实。

## 8. 安全事件闭环

### 8.1 业务流程

```text
发现异常
  → 创建事件
  → 主代理读取状态并分配任务
  → 调查实际影响
  → 溯源攻击路径
  → 汇总证据并形成处置计划
  → 操作申请结构化
  → 确定性策略校验
  → 人工审批
  → 受控执行
  → 回读状态与恢复验证
  → 审计汇报
  → 关闭事件或带新目标重新调查
```

### 8.2 每一步的输入、负责人、输出与存在理由

| 步骤 | 输入 | 负责人 | 输出 | 为什么存在 |
|---|---|---|---|---|
| 数据进入 | Official PCAP、Synthetic CI/云事件、Mock 状态事件 | 安全连接器 | 带来源标识的 Raw Event | 保留原始事实，防止后续分析失去出处 |
| 发现风险 | Raw Event、检测规则和模型分类结果 | 静默监测子代理 | Security Signal + EvidenceReference | 把海量事件收敛为可解释的风险线索 |
| 创建事件 | 一个或多个满足创建条件的 Signal | 事件管理器 | SecurityIncident（NEW/DETECTED） | 给后续任务提供统一事件 ID 和状态 |
| 生成任务 | 事件摘要、Confirmed Fact、未决问题 | 主代理 | AgentTask | 说明为何调查、允许看什么、希望返回什么 |
| 调查影响 | AgentTask、授权 EvidenceReference | 事件调查子代理 | AgentResult/Agent Finding | 判断凭据是否被用、影响是什么；不直接授权动作 |
| 还原路径 | 时间、实体和证据引用 | 攻击溯源子代理 | 带引用的 Timeline/Agent Finding | 解释 CI、来源、凭据、API、资源之间的因果顺序 |
| 确认事实 | 新证据、Finding、反证 | 主代理提出，事件管理器校验 | Confirmed Fact 或 Unresolved Question | 防止把 LLM 解释直接写成安全事实 |
| 形成建议 | Confirmed Fact、风险与业务影响 | 主代理 | Action Recommendation | 把调查结果转换为可讨论的处置方向 |
| 生成申请 | Action Recommendation、动作对象 | 操作执行子代理 | ActionRequest | 将自然语言建议变成可校验的固定格式申请 |
| 策略判断 | ActionRequest、权限、状态和白名单 | 确定性策略引擎 | PolicyDecision | 让可测试规则而非模型承担放行条件检查 |
| 人工审批 | 证据摘要、风险、业务影响和 PolicyDecision | 授权审批人员 | ApprovalRecord | 对高风险副作用承担最终业务责任 |
| 受控执行 | 已批准申请 | 受控执行接口/Mock/沙箱 | ExecutionResult | 限制动作能力并保留真实执行回执 |
| 恢复验证 | ExecutionResult 与状态查询 | 系统验证节点；主代理读取结果 | VerificationResult | 证明风险消除和业务恢复，不把 success 当作结束 |
| 审计与关闭 | 全部结构化记录 | 审计汇报子代理 + 事件管理器 | Audit Report、CLOSED 或重新调查 | 保证可追溯，并让未通过验证的事件回到正确阶段 |

### 8.3 事件状态机

【建议】沿用开发方案给出的状态序列，并在实现时由事件管理器约束合法迁移：

```text
NEW → DETECTED → INVESTIGATING → ATTRIBUTED
    → CONTAINED → ROTATED → VERIFIED → CLOSED
```

状态名称表达业务阶段，不代表每个事件都必须机械经过全部节点。例如证据不足的事件可停留在调查阶段并由人工关闭；无需轮换的事件不应为了走完流程伪造动作。

| 状态 | 表示什么 | 允许进入所需事实 | 谁提出迁移 | 谁校验写入 | 失败或不足时怎么办 |
|---|---|---|---|---|---|
| NEW | 已创建事件，但风险尚未完成检测确认 | 至少一个满足创建规则的 Signal | 静默监测子代理或系统连接器 | 事件管理器 | 输入无效则记录拒绝原因，不进入 DETECTED |
| DETECTED | 已确认存在需要调查的风险信号 | Signal 可回指 Raw Event，触发规则可解释 | 静默监测子代理/主代理 | 事件管理器 | 证据不可回查则保持 NEW 或人工关闭 |
| INVESTIGATING | 调查任务已开始 | 存在有效 AgentTask 和授权证据范围 | 主代理 | 事件管理器 | 工具失败、权限不足或数据不可用时记录未决项并停止自动调查 |
| ATTRIBUTED | 技术攻击路径和影响对象已得到足够证据支持 | 时间线、关键实体关系和影响事实可回指 Evidence | 主代理 | 事件管理器 | 不是现实攻击者身份归因；证据不足则留在 INVESTIGATING |
| CONTAINED | 已完成遏制动作并确认攻击能力受限 | 已批准 ActionRequest + 成功 ExecutionResult + 初步回读 | 主代理/执行结果处理节点 | 事件管理器 | 执行失败返回审批/执行或调查，不得继续标记成功 |
| ROTATED | 泄露凭据已完成轮换 | 旧/新 Key 状态和轮换执行记录存在 | 主代理/验证节点 | 事件管理器 | 新 Key 不可用时保持 CONTAINED 并转人工恢复 |
| VERIFIED | 安全与业务恢复断言全部通过 | 旧 Key、恶意调用、新 Key、合法 CI、异常资源五类验证有结果 | 主代理/验证节点 | 事件管理器 | 任一关键断言失败则返回调查、处置或人工处理 |
| CLOSED | 事件处理结束并形成审计记录 | VERIFIED，或人工基于充分理由强制关闭且留痕 | 主代理或人工 | 事件管理器 | 不允许无审计关闭；重新出现相关 Signal 时创建新事件或按规则重开 |

【待设计】合法迁移表的代码级守卫、具体证据数量、时间窗、置信度阈值、超时状态和人工强制修改规则。现有官方数据无法为这些阈值提供充分依据。

### 8.4 闭环完成条件

本标杆事件只有同时满足以下条件，才能被认为完成：

- 泄露路径与异常调用之间存在可复核证据；
- 敏感数据读取和高费用资源创建的影响已确认或明确排除；
- 高风险操作经过策略校验和必要审批；
- 执行结果已通过受控接口回读；
- 旧 Key 已失效，异常调用已停止；
- 新 Key 可用，合法业务已恢复，或未恢复原因已记录并升级人工处理；
- 事件全过程可从审计记录重放。

### 8.5 失败、重新规划与调查停止

主代理可以根据执行回读或新证据再次调度相关子代理，但必须说明新的任务目标和触发原因。模型超时、工具失败、知识检索失败或证据不足时，不得自动放行高风险动作。

出现以下任一条件时，应停止当前自动调查并保存状态：

- 核心调查问题已经回答，继续查询不会改变处置判断；
- 关键证据已经获得，可进入下一业务阶段；
- 连续查询没有产生新增 Evidence 或 Confirmed Fact；
- 数据源不可用、工具调用失败或结果无法校验；
- 当前 Agent 权限不足，且不能在既有权限模型内完成；
- 已达到本次事件配置的时间、调用或成本预算；
- 不同证据或 Agent Finding 存在实质冲突；
- 需要人工判断业务影响、例外情况或高风险动作。

停止不等于关闭事件。系统应记录停止原因、已回答问题、未决问题和建议的人工下一步。具体调用次数和预算值【待设计】，本基线不填写无依据数字。

【待验证】比赛 Demo 是否在五分钟主流程中展示一次失败分支，取决于编排稳定性和演示时长；该分支不是首个可运行版本的必选项。

## 9. 多智能体体系

### 9.1 为什么采用多智能体

本产品使用多智能体的首要原因是建立安全边界，而非增加角色数量：

- **职责隔离**：监测、调查、溯源、操作申请和审计各自承担清晰任务；
- **数据隔离**：每个子代理只接收当前任务需要的事件摘要和证据引用；
- **权限隔离**：只读调查能力与有副作用的受控执行能力分离；
- **风险隔离**：某个模型误判或受到输入污染时，无法获得完整数据和系统控制权；
- **模型能力匹配**：分类、检索、结构化整理和流程编排可使用不同模型能力；
- **可审计**：每次调度都有任务、输入范围、输出结构和状态影响。

因此，多智能体在本项目中首先是安全架构，其次才是 AI 协作架构。

### 9.2 主代理

| 项目 | 内容 |
|---|---|
| 为什么需要它 | 安全事件不是固定流水线，需要一个角色根据当前事实、未决问题和任务依赖统一规划，但该角色不应成为超级管理员 |
| 输入 | SecurityIncident、Security Signal、Confirmed Fact、AgentResult、未决问题、人员指令 |
| 可以看到的数据 | 事件状态中枢中的脱敏摘要、证据引用、任务与结果；不默认读取完整原始 PCAP 或全部原始日志 |
| 不允许看到的数据 | 明文 API Key、未经租户授权的数据、与当前事件无关的完整对话或原始数据 |
| 可以调用的能力 | 在预定义范围内创建 AgentTask、调度子代理、读取事件状态、提出状态迁移和 Action Recommendation、解释进度 |
| 禁止操作 | 直接冻结/轮换、修改云资源、自行扩权、绕过策略或审批、把 Finding 直接写成无证据的 Confirmed Fact |
| 输出 | AgentTask、调度计划、汇总结论、未决问题、Action Recommendation、状态迁移建议 |
| 对事件状态的贡献 | 提出迁移和下一步，不直接写入受保护状态；由事件管理器校验 |

### 9.3 子代理划分


#### 9.3.1 静默监测子代理

| 项目 | 内容 |
|---|---|
| 为什么需要它 | 后台数据持续进入，需要先用低成本、只读能力识别风险线索，避免主代理处理每条原始事件 |
| 输入 | Official PCAP 解析后的网络事件；Synthetic CI、云 API、认证和资源事件 |
| 可以看到的数据 | 包/流元数据、明文 HTTP/DNS/数据库字段、脱敏 CI/云事件；官方数据实际使用 PCAP、PCAP-NG 解析结果 |
| 不允许看到的数据 | 明文 Key、与检测无关的租户业务正文、操作凭据和执行接口 |
| 可以调用的能力 | 只读流量解析结果查询、规则匹配、分类/抽取模型、统计计数 |
| 禁止操作 | 完整调查、攻击归因、冻结、轮换、修改资源、直接关闭事件 |
| 输出 | Security Signal、触发原因、对象摘要、EvidenceReference、初始风险等级 |
| 对事件状态的贡献 | 可建议创建 NEW 或推进 DETECTED；事件管理器校验后写入 |

#### 9.3.2 事件调查子代理

| 项目 | 内容 |
|---|---|
| 为什么需要它 | Signal 只是风险线索，需要独立只读角色确认“是否真的发生、影响是什么” |
| 输入 | AgentTask、事件摘要、EvidenceReference、具体调查问题 |
| 可以看到的数据 | 授权 PCAP 包/流与请求响应、Synthetic 云审计/资源事件、Mock 只读状态；官方数据实际用于回查时间、IP、URI、响应等网络事实 |
| 不允许看到的数据 | 明文 Key、无关租户数据、策略密钥、可产生副作用的接口凭证 |
| 可以调用的能力 | 证据查询、请求响应重组结果、只读资源/凭据状态查询、结构化事实整理 |
| 禁止操作 | 执行处置、修改证据、仅凭文件名或模型输出确认攻击成功 |
| 输出 | Agent Finding、EvidenceReference、支持证据、反证、影响判断、未决问题、置信度 |
| 对事件状态的贡献 | 为 INVESTIGATING、ATTRIBUTED 提供候选事实；不能自行改变状态 |

#### 9.3.3 攻击溯源子代理

| 项目 | 内容 |
|---|---|
| 为什么需要它 | 分散事实需要按时间和实体关系排列，才能解释攻击入口、使用路径与影响之间的联系 |
| 输入 | AgentTask、Confirmed Fact、EvidenceReference、实体标识和时间范围 |
| 可以看到的数据 | Official PCAP 中同一抓包的时间戳、五元组和请求响应；Synthetic CI—Runner—Credential—Resource 事件 |
| 不允许看到的数据 | 明文 Key、未经授权的完整流量库、现实人员隐私和处置接口 |
| 可以调用的能力 | 证据检索、相似记录召回、时间排序、关系解释 |
| 禁止操作 | 把相同 IP 的不同 PCAP 强行关联；仅凭模型认定现实攻击者/组织；执行处置 |
| 输出 | 技术时间线、实体关系、每一步 EvidenceReference、缺失链路和替代假设 |
| 对事件状态的贡献 | 为 ATTRIBUTED 提供技术路径依据；不承担执法或现实身份归因 |

#### 9.3.4 操作执行子代理

| 项目 | 内容 |
|---|---|
| 为什么需要它 | 把分析建议与有副作用动作隔开，并将自然语言收敛成可校验申请 |
| 输入 | 已确认 Action Recommendation、事件对象、前置事实、允许动作模板 |
| 可以看到的数据 | 动作所需的脱敏对象 ID、策略结果、审批状态和 Mock/沙箱执行结果；不需要官方 PCAP 原始载荷 |
| 不允许看到的数据 | 明文 Key、无关调查数据、策略管理密钥、未批准动作的执行凭证 |
| 可以调用的能力 | 生成/提交 ActionRequest，查询 PolicyDecision、ApprovalRecord、ExecutionResult 和 VerificationResult |
| 禁止操作 | 自行决定动作、批准自己、绕过策略、直接调用底层冻结/轮换接口、扩大动作范围 |
| 输出 | ActionRequest、申请状态、执行结果引用和验证请求 |
| 对事件状态的贡献 | 提供进入 CONTAINED/ROTATED 的执行事实，但状态仍由事件管理器校验 |

#### 9.3.5 审计汇报子代理

| 项目 | 内容 |
|---|---|
| 为什么需要它 | 将分散的 Signal、证据、任务、审批和验证记录整理为人员可读报告，同时保持事实不可篡改 |
| 输入 | 只读事件状态、审计记录和脱敏 EvidenceReference |
| 可以看到的数据 | Official capture 引用、Synthetic 来源标识、Mock 执行记录、AgentTask/Result、策略和审批记录 |
| 不允许看到的数据 | 明文 Key、无关租户数据、被权限策略隐藏的原始内容 |
| 可以调用的能力 | 只读查询、脱敏、结构化汇总和报告生成 |
| 禁止操作 | 修改或删除底层 Evidence/AuditRecord、执行资源操作、替代事件管理器关闭事件 |
| 输出 | 事件报告、审计时间线、数据来源说明、未决风险和复盘项 |
| 对事件状态的贡献 | 为 CLOSED 提供报告完整性条件；不能单独决定关闭 |

【待设计】每类子代理的具体工具清单、字段级数据权限、超时重试与冲突处理规则尚未冻结。

### 9.4 为什么不按安全产品类型划分一级 Agent

身份、API、端点、网络等分类适合描述数据域，但不天然形成权限边界。例如“API Agent”既可能查询日志，也可能修改 API 权限，职责容易膨胀。当前按安全工作阶段划分后，读取事实、还原关系、提出操作、执行控制和生成审计分别归属不同主体，更容易限制权限和证明风险隔离。

旧版能力不被简单删除，而是下沉：

- 身份与 API 研判成为事件调查子代理使用的数据、规则和只读工具；
- 攻击链还原成为攻击溯源子代理的内部能力；
- 处置规划由主代理基于证据形成，操作执行子代理只负责结构化申请；
- 验证与重规划由受控回读、事件状态和主代理条件调度共同承担；
- 端点与横向移动不属于当前攻击链，作为未来数据源和调查工具扩展。

### 9.5 协作与通信规则

- 子代理不能直接互相通信、调度或转交权限；
- 所有结果先写入事件状态中枢，再由主代理读取并决定下一步；
- 主代理只传递事件摘要、证据引用、任务目标和返回格式，不传递完整历史对话；
- 子代理统一返回任务完成状态、结论、证据、风险或置信度、未决项、下一步建议和审批需求；
- 子代理建议不等同于事件决策，最终流程推进由主代理提出、事件管理器校验。

### 9.6 AgentTask 与 AgentResult 协作契约

【建议】主代理给子代理的 AgentTask 至少表达：

| 内容 | 产品含义 |
|---|---|
| `incident_id` | 任务属于哪个安全事件 |
| `task_goal` | 本次必须回答的一个明确问题 |
| `allowed_context` | 允许读取的事件摘要和数据范围 |
| `evidence_refs` | 可回查的既有证据入口 |
| `allowed_tools` | 本次任务可调用的固定工具子集 |
| `expected_output` | 要求返回的结构化结果类型 |

AgentTask 不是临时授权机制。`allowed_tools` 只能从该 Agent 预先批准的白名单中缩小，不能扩大权限。具体 Schema【待设计】。

【建议】AgentResult 至少表达：

| 内容 | 产品含义 |
|---|---|
| `task_status` | 完成、部分完成、失败、权限不足或需要人工 |
| `findings` | Agent 对本次问题的分析结果，不自动等于事实 |
| `evidence_refs` | 支持或反驳 Finding 的证据引用 |
| `confidence/risk` | 对分析可靠程度或风险的表达，不是授权分数 |
| `unresolved_questions` | 仍缺少哪些事实 |
| `next_step` | 建议下一调查或处置方向 |
| `approval_required` | 是否涉及需审批的动作 |

AgentResult 只是一次任务结果，不是整个事件的最终裁决。主代理可以汇总它，事件管理器必须依据证据和规则决定事实、状态及后续流程。具体字段和枚举【待设计】。

## 10. 智能体可信治理

### 10.1 当前治理目标

可信治理的目标不是证明模型永不出错，而是确保模型出错、被误导或工具失败时，影响范围仍然受控，关键动作仍需通过确定性检查并可追溯。

### 10.2 当前纳入产品的控制

【已确认】本阶段包含：

- 每类子代理职责固定、工具权限预先固定；
- 主代理只能分配权限范围内的任务，不能临时扩权；
- 子代理禁止自由通信和相互调度；
- 原始明文 API Key 不进入模型上下文和普通日志；
- 监测、调查、溯源、审计默认只读；
- 操作执行子代理只能生成申请和查询结果，不能直接实施高风险动作；
- 冻结、轮换和资源操作必须经过确定性策略；
- 生产环境高风险动作必须人工审批；
- 证据、调度、状态修改、审批和执行全过程留痕；
- 权限不足、模型失败、工具失败或证据不足时，不得绕过限制或自动放行。

### 10.3 事件状态的完整性控制

- 子代理只能追加授权范围内的证据摘要和结果，不能覆盖其他代理记录；
- 主代理可纠正错误或解除阻塞，但必须记录修改前后内容和原因；
- 人工拥有最高修改权限，但修改同样必须说明原因并留痕；
- 被删除内容不参与当前判断，但保留在审计记录中；
- 状态变更由主代理提出，事件管理器二次校验后写入。

### 10.4 当前不宣称已经实现的治理能力

【后续扩展】以下思想有价值，但不属于当前 Demo 已确认能力：

- 完整 Agent PKI、独立证书和凭证生命周期；
- 跨组织 Agent 身份联盟；
- MCP Server 签名、工具包供应链验证和完整准入市场；
- 覆盖所有提示注入、RAG 投毒和数据外传路径的防护体系；
- 独立的大规模 Agent 行为监控与自动熔断中心。

比赛材料可将其描述为治理路线图，不得描述为已经开发完成。

## 11. 总体产品架构

```text
Official PCAP / Synthetic CI与云事件 / Mock凭据与资源状态
                         ↓
              安全连接器 + 来源标识与脱敏
                         ↓
                  事件总线与审计存储
                         ↓
                   静默监测子代理
                         ↓
             主代理 / LangGraph 有状态编排
                         ↕
                   事件状态中枢
          ↙              ↓              ↘
   事件调查子代理   攻击溯源子代理   审计汇报子代理
                         ↓
                 主代理形成处置计划
                         ↓
                   操作执行子代理
                         ↓
                   确定性策略引擎
                         ↓
                      人工审批
                         ↓
                   受控执行接口
                         ↓
              状态回读、恢复验证与审计
```

### 11.1 各层存在的原因

| 层级 | 为什么存在 |
|---|---|
| 数据源层 | Official 提供真实网络证据，Synthetic 补齐缺失业务事件，Mock/沙箱提供动态执行状态；三者始终分开标识 |
| 安全连接器 | 承担授权接入、格式适配、脱敏和来源标识，不让模型直接接触所有原始系统 |
| 事件总线与审计存储 | 解耦数据接入与分析，并保存不可依赖模型记忆替代的原始记录 |
| 静默监测子代理 | 在后台把连续事件转换为可解释的结构化风险信号 |
| 主代理与 LangGraph | 根据事件状态进行条件调度、暂停、恢复和结果汇总；具体图结构由开发设计 |
| 事件状态中枢 | 为所有角色提供同一份结构化业务事实，避免共享完整对话和重复转述失真 |
| 调查、溯源、审计子代理 | 在只读权限内分别确认影响、还原路径、生成报告 |
| 操作执行子代理 | 将自然语言建议收敛为可校验的固定格式申请 |
| 确定性策略引擎 | 用可测试规则校验高风险动作，防止模型成为授权器 |
| 人工审批 | 承担业务影响和例外情况的最终责任判断 |
| 受控执行与验证 | 限制副作用，并通过真实回读判断风险是否解除、业务是否恢复 |

### 11.2 LangGraph 的产品定位

【已确认】LangGraph 用于主代理的有状态流程编排，因为本产品需要明确节点、条件路由、暂停审批和恢复执行，而不是无边界的 Agent 循环。

【待设计】具体图节点、并行分支、检查点存储、超时重试、暂停恢复和前端连接方式由开发阶段确定。设计文档不预先画死代码级图结构。

## 12. 数据、证据与事件状态

### 12.1 产品所需数据入口与当前可用来源

| 产品所需入口 | 目标用途 | 当前比赛来源 | 当前边界 |
|---|---|---|---|
| 租户 CI 安全事件 | Action 版本/Digest、权限、Runner 与 Secret 访问 | Synthetic | 官方 data 不提供；未来真实连接器待接入 |
| 云 API 审计 | Key 调用时间、来源、接口、资源和结果 | Synthetic | 只使用 Key ID/指纹，不向模型提供明文 Key |
| 网络流量 | IP、端口、协议、HTTP/DNS/数据库行为 | Official PCAP | 可真实回查包/流；不能自动解释为云 Key 使用 |
| 认证事件 | 设备、地区、认证结果、会话 | Synthetic；Official 仅有少量网络认证痕迹 | 官方无统一用户/credential_id |
| 资源操作/费用事件 | 数据读取、资源创建、权限和费用影响 | Synthetic + Mock 状态 | 官方不支持云资源语义 |
| 凭据状态服务 | 有效、冻结、轮换、新旧 Key 状态 | Mock/沙箱 | 只用于演示受控动态状态，不声称生产处置 |

### 12.2 从原始数据到处置建议的概念链

```text
Raw Event
  → Security Signal
  → EvidenceReference
  → Confirmed Fact
  → Agent Finding
  → Risk Assessment
  → Action Recommendation
```

| 概念 | 定义 | 例子 | 不能被误解为 |
|---|---|---|---|
| Raw Event | 数据源产生或重放的原始记录 | PCAP 中某个包/HTTP 请求；Synthetic CI 事件；Mock 状态事件 | 已经确认的攻击 |
| Security Signal | 规则或模型从 Raw Event 中识别的风险线索 | 某 URI 含注入表达式；新来源调用敏感接口 | 最终事实或处置授权 |
| EvidenceReference | 能稳定回查原始记录的位置和来源 | capture_id + flow/packet 定位；Synthetic event_id | LLM 摘要或复制粘贴文本 |
| Confirmed Fact | 由可回查证据支持、经事件管理器校验后写入的事实 | “某来源在某时刻调用某接口” | “攻击者是谁”等无证据推断 |
| Agent Finding | Agent 基于事实和证据形成的分析结果 | “该调用与历史用途不一致，疑似 Key 滥用” | 自动成立的 Confirmed Fact |
| Risk Assessment | 综合事实、影响和不确定性的风险判断 | 高风险，原因是数据读取与资源创建同时出现 | 冻结许可 |
| Action Recommendation | 对下一步处置方向的建议 | 建议冻结旧 Key 并启动轮换 | 已批准的 ActionRequest |

**LLM 输出不是 Evidence。Agent Finding 也不天然等于 Confirmed Fact。** 重要判断必须能够沿 EvidenceReference 回到 Official、Synthetic 或 Mock/沙箱中的原始记录，并显示来源类型。

### 12.3 EvidenceReference 的产品要求

【建议】每条 EvidenceReference 至少能够表达：

- 证据属于哪个 incident；
- `source_type` 是 `OFFICIAL`、`SYNTHETIC` 还是 `MOCK_SANDBOX`；
- 原始数据源和不可歧义的定位信息；
- 采集/事件时间与进入系统时间；
- 证据摘要和脱敏状态；
- 完整性校验或内容哈希；
- 当前哪些 Agent 有权读取详情。

对官方 PCAP，定位至少要区分 capture 文件与其中的 flow/packet/请求响应。具体字段、TCP 流重组后的偏移定位和哈希算法【待设计】。

### 12.4 事件状态中枢：结构化 Single Source of Truth

事件状态中枢是整个系统的结构化 **Single Source of Truth（唯一事实来源）**，不是聊天历史，也不把模型上下文当作安全数据库。

【建议】产品层至少分为：

```text
incident              事件标识、当前状态、等级与责任人
signals               风险信号及触发原因
confirmed_facts       已校验事实
evidence              EvidenceReference 与来源标识
agent_tasks           主代理下发的任务
agent_results         子代理任务结果和 Finding
hypotheses            待证伪解释，不属于事实
unresolved_questions  未决问题和证据缺口
pending_actions       Action Recommendation / ActionRequest
approval_records      策略与人工审批记录
execution_results     受控执行结果
verification_results  恢复验证断言与结果
audit_records         调度、读取、修改和状态迁移记录
```

字段 Schema【待设计】。任何界面摘要都应从上述结构化状态生成，不得依赖某次模型对话才能恢复事件事实。

### 12.5 状态中枢写入与修改规则

- 子代理只能追加其任务范围内的 AgentResult 和 EvidenceReference，不能直接确认全局事实；
- 主代理可提出 Confirmed Fact、状态迁移和纠错建议；
- 事件管理器依据 Schema、证据存在性和状态规则校验后写入；
- 人工强制修改必须记录修改前内容、修改后内容、原因和操作者；
- 被逻辑删除内容不参与当前判断，但保留在 AuditRecord 中；
- Official/Synthetic/Mock 的 `source_type` 不允许被 Agent 或人工无痕改写。

### 12.6 异常信号与证据规则

官方 PCAP 可支持明文恶意 URI/参数、异常通信方向、同一抓包内频率、DNSLog 或特定网络攻击行为等 Signal。Synthetic 主事件可提供新来源、调用时间偏移、首次访问敏感接口、首次创建高费用资源、调用紧跟 CI 变化等信号。

【待设计】检测规则、历史基线、字段规范、关联时间窗、证据权重、置信度阈值和状态升级阈值。官方数据多数为短攻击片段且没有正常组，不能为长期行为基线和误报阈值提供充分依据。模型可参与分类、排序和解释，但不能单独决定冻结、轮换或放行。

### 12.7 开发数据来源矩阵

| 产品能力 | 所需数据 | Official data | Synthetic | Mock/沙箱 | 当前可开发性 |
|---|---|---|---|---|---|
| PCAP 接入与规范化 | 包时间、IP、端口、协议、载荷 | 已有 | 不需要 | 不需要 | 可直接进入详细设计 |
| 网络 Security Signal | 解析事件、规则和样本 | 已有攻击样本；标签不完整 | 可补正常/边界样例并明确标识 | 不需要 | 部分可开发，评测集待设计 |
| CI 异常 Signal | Action、Digest、Runner、Secret 访问 | 没有 | 必须 | 不需要 | 可按 Synthetic 开发 |
| Key 异常调用调查 | credential_id、来源、API、结果 | 只有不带 Key 身份的网络请求 | 必须 | 可提供只读状态 | 可按组合数据开发 |
| 敏感数据影响 | 数据对象、分类、访问结果 | 仅部分 HTTP/SQL 行为线索 | 必须提供云业务事实 | 可提供状态 | 可按 Synthetic 开发 |
| 高费用资源影响 | resource_id、类型、数量、费用 | 没有 | 必须提供事件 | 必须维护动态资源状态 | 可 Mock 开发 |
| 网络时间线 | 时间戳、五元组、请求响应 | 同一 PCAP 内已有 | 可补跨域节点 | 不需要 | 局部可直接开发 |
| CI—Key—云资源时间线 | 跨源实体 ID 与时间 | 没有 | 必须 | 提供动作后状态 | 可按 Synthetic 开发 |
| 冻结/轮换 | Key 状态和受控动作 | 没有 | 只提供申请前上下文 | 必须 | 可 Mock/沙箱开发 |
| 恢复验证 | 旧/新 Key、恶意调用、合法 CI、资源状态 | 没有动态状态 | 可提供验证请求 | 必须 | 可 Mock/沙箱开发 |
| 审计闭环 | Signal、Task、Result、Decision、Approval、Execution、Verification | 提供原始证据引用 | 提供业务事件 | 提供动态执行记录 | 系统运行时可开发 |

当前不要求先建设完整证据图数据库。实体关系可先以结构化字段和 EvidenceReference 表达；是否引入图存储应由查询复杂度和 Demo 价值决定。

## 13. 工具与外部能力接入

### 13.1 选择原则

技术形式由稳定性、风险和调用主体决定，不把所有外部能力统一包装为 MCP。

| 形式 | 适用能力 | 本项目定位 |
|---|---|---|
| MCP | 需要模型按标准描述发现和调用、可严格限定参数的工具，优先只读调查能力 | 【待设计】是否使用及首批工具清单尚未冻结 |
| OpenAPI | 稳定、强鉴权、可审计的系统集成、批量同步、状态查询和受控操作 | 适合安全连接器、凭据状态服务、审批与执行接口 |
| 普通内部函数 | 证据标准化、字段脱敏、确定性规则、状态迁移校验等纯内部逻辑 | 不需要为增加“AI 感”而改造成 MCP |
| Mock Adapter | 比赛环境中的冻结、轮换、恢复和状态回读 | 【已确认】用于避免操作真实生产凭据与资源 |
| LangGraph Node | 有明确输入、输出和状态影响的流程步骤或受限子代理节点 | 承担编排单元，不等同于外部工具协议 |

### 13.2 接入安全原则

- 每个工具的可调用角色和风险等级预先固定；
- 输入参数使用结构化 Schema，并在执行前校验；
- 查询结果保留来源和时间，不把不可信内容当成系统指令；
- 高风险动作只能进入操作申请—策略—审批—受控执行链；
- 工具失败和超时写入事件状态，不得被模型解释为操作成功。

## 14. 风险操作控制与恢复验证

### 14.1 当前高风险动作

本阶段围绕标杆事件只设计：

- 冻结疑似泄露的 API Key；
- 轮换 API Key；
- 恢复或更新合法业务所需的凭据状态；
- 查询旧 Key、新 Key、异常调用和业务恢复状态。

自动修改真实生产资源、任意 Shell、EDR 隔离、全局防火墙封禁等不在当前范围。

### 14.2 操作控制链

```text
Investigation
  → Agent Finding
  → Action Recommendation
  → ActionRequest
  → PolicyDecision
  → Human Approval
  → Controlled Execution
  → ExecutionResult
  → VerificationResult
```

这是全文唯一处置链。不存在“LLM 判断有攻击后直接冻结 Key”的旁路。

### 14.3 确定性策略与模型的边界

| 决策主体 | 负责什么 | 一句话解释 |
|---|---|---|
| AI/模型 | 分类、抽取、检索、排序、解释、调查规划、证据整理、时间线生成、操作建议、申请生成和报告生成 | 模型负责帮助人和系统理解复杂信息，但它的输出需要证据与规则约束 |
| 确定性系统 | 权限与 Schema 校验、状态迁移、动作白名单、策略规则、审批要求、受控执行和结果回读 | 确定性系统像“不可跳过的安全闸门”，相同输入应得到可测试的控制结果 |
| 人工 | 高风险操作最终批准、业务影响判断、例外处理和强制决策 | 人工承担模型和规则无法理解的业务责任，任何强制修改都必须留痕 |

模型可以解释风险、推荐动作和填写申请，但以下判断必须由规则、权限系统或人工完成：

- 调用者是否有权申请该动作；
- 动作对象是否与当前事件一致；
- 必要证据和前置状态是否存在；
- 是否需要人工审批；
- 参数是否在允许范围内；
- 执行接口是否为准入接口；
- 操作是否真正成功。

【待设计】具体策略规则、风险分级、双人审批需求和参数白名单尚未冻结。

### 14.4 验证断言

**接口返回 `success` 只说明一次调用得到成功响应，不说明安全事件已经解决。** Demo 至少展示以下机器可读断言：

- `old_key_active == false`；
- 使用旧 Key 的测试调用被拒绝；
- 攻击来源后续异常调用停止或失败；
- `new_key_active == true`；
- 合法 CI 测试任务使用新 Key 成功；
- 高费用资源不再继续创建；
- 每个断言都能指向回读记录。

上述动态结果全部来自 Mock/沙箱状态服务，不来自官方离线 PCAP。Official 数据只作为处置前网络证据保留；Mock/沙箱必须真正维护动作前后不同的状态，而不是前端播放成功文案。

字段名、验证请求、超时处理和测试方式由 Mock/沙箱接口详细设计确定。任一关键断言失败时，事件不得进入 VERIFIED/CLOSED，应返回调查、处置或人工恢复。

## 15. 比赛 Demo 设计

### 15.1 Demo 要证明什么

五分钟 Demo 不以聊天内容为核心，而要证明：系统收到了什么信号、为何调用某个 Agent、Agent 看到了哪些授权数据、结论依据是什么、事件状态如何变化、为何高风险动作被暂停、执行后是否真正恢复。

### 15.2 Demo 数据来源显示规则

界面中的每一条 Raw Event、EvidenceReference 和动态状态都必须显示来源徽标：

- `OFFICIAL`：比赛方 PCAP 或其确定性解析结果；
- `SYNTHETIC`：团队为补齐 CI/云业务链构造的事件；
- `MOCK/SANDBOX`：演示环境中的凭据、资源、执行和恢复状态；
- `SYSTEM`：系统运行产生的 Task、Result、Policy、Approval 和 Audit 记录。

来源徽标不是装饰，而是审计事实。报告中也必须说明每个结论使用了哪类数据。

### 15.3 五分钟主流程

| 阶段/时间建议 | 画面与动作 | 数据来源 | 必须证明什么 |
|---|---|---|---|
| Signal 0:00–0:35 | 重放 CI Action 异常、云 API 异常；可并列展示一条官方 PCAP 网络 Signal | Synthetic；Official 可作独立网络证据 | 发生了什么、来自哪里，官方与合成没有混淆 |
| Detection 0:35–1:05 | 静默监测子代理输出告警，主代理选择调查任务 | System + 对应 Evidence | 为什么异常、证据在哪里、为何调用下一 Agent |
| Investigation 1:05–1:55 | 调查子代理确认 Key 滥用、敏感数据读取和高费用资源创建 | Synthetic 云审计/资源事件；Official 只证明其实际网络行为 | Finding、证据、反证/未决项和状态变化 |
| Attribution 1:55–2:35 | 溯源子代理展示 Action—Runner—Credential—Source—API—Resource 时间线 | Synthetic 跨域链 + Official 局部网络时间线 | 每个节点能回指其真实来源，不伪造官方缺失部分 |
| Action 2:35–3:15 | 主代理建议冻结/轮换，操作子代理生成 ActionRequest | System | 建议与申请分离，模型没有执行权限 |
| Approval 3:15–3:45 | 策略校验后暂停，人工查看证据并批准 | System | 未审批前 Key/资源状态完全不变 |
| Execution 3:45–4:20 | 受控接口在演示环境冻结旧 Key、创建新 Key/轮换状态 | Mock/Sandbox | Mock 状态真实改变且有 ExecutionResult |
| Verification 4:20–4:50 | 回读旧 Key、新 Key、恶意调用、合法 CI 和资源创建状态 | Mock/Sandbox | 验证断言决定是否进入 VERIFIED，不只显示 success |
| Audit 4:50–5:00 | 展示 Signal、Evidence、Task、Finding、Decision、Approval、Execution、Verification | System + 三类数据引用 | 完整可追溯，并明确每项事实的来源 |

具体秒数可根据实测调整，但不应删除策略审批和恢复验证两个关键证明点。

### 15.4 Demo 界面建议

【建议】最小前端采用四个稳定区域，而不是多个聊天窗口：

1. **事件时间线**：显示信号、调度、审批、执行和状态变化；
2. **证据与攻击链**：显示关键实体关系、结论和可点击证据引用；
3. **Agent 任务面板**：显示为何调用、输入范围、工具权限、结构化输出；
4. **审批与验证面板**：显示策略结果、人工动作、执行回读和恢复断言。

不展示模型隐藏推理过程，不把预先写好的自然语言长文当作核心输出。

### 15.5 Demo 可复现要求

- 使用固定但可重放的事件数据集；
- 每次运行重新产生事件、任务、审批和执行记录；
- 关键节点由真实程序状态推进，不以视频或前端定时动画替代；
- Mock Adapter 必须维护可查询状态，使冻结、轮换和恢复前后结果不同；
- 支持演示人员查看证据详情和审计记录；
- 若模型不可用，系统应安全失败并保持高风险动作未执行。
- 官方 PCAP 的原始文件和解析 Evidence 可回查；Synthetic/Mock 必须始终显示来源标签；
- 主 Golden Path 与官方 NTA 样本验证路径可以使用同一事件框架，但不得把两个独立样本伪造成同一真实攻击。

【待验证】LangGraph、事件状态中枢、前端和模型能否在五分钟内稳定完成全流程，是下一阶段首要工程验证项。

## 16. 创新点与评价指标

### 16.1 可成立的创新点

#### 创新一：按安全工作阶段与权限边界构建多智能体协作

- **现实问题**：单一智能体若同时获得全部数据和操作权限，误判或被注入后的影响过大。
- **设计**：监测、调查、溯源、操作申请、审计角色分离，子代理工具权限固定且禁止自由通信。
- **实现载体**：主代理受控调度、结构化任务、事件状态中枢和权限检查。
- **Demo 证据**：界面可展示各 Agent 获得的数据范围、工具权限，以及调查 Agent 无法执行冻结。

#### 创新二：CI 供应链异常与云侧 API 滥用的跨域证据关联

- **现实问题**：泄露线索与实际损害分属 CI 和云侧，单域告警难以确认攻击成功。
- **设计**：以同一事件关联 Action、Runner、Key 标识、来源、API 调用、数据与资源操作。
- **实现载体**：安全连接器、证据引用、时间线和事件状态。
- **Demo 证据**：两条独立 Synthetic 业务信号逐步形成可回放攻击链；Official PCAP 只强化网络证据解析与引用能力，不冒充 CI/云日志。

#### 创新三：模型判断与确定性授权解耦的有界自治

- **现实问题**：模型适合整理和解释，但不适合承担高风险操作授权。
- **设计**：模型只生成调查结果、建议和操作申请；策略引擎与人工决定是否执行。
- **实现载体**：结构化申请、确定性策略、审批暂停恢复、受控接口。
- **Demo 证据**：未审批前凭据状态不变，模型或主代理不能绕过流程。

#### 创新四：以恢复断言结束事件的可验证闭环

- **现实问题**：工具返回成功不能证明风险消除或业务恢复。
- **设计**：关闭前同时验证旧 Key、恶意调用、新 Key 和合法业务状态。
- **实现载体**：凭据状态服务、Mock/沙箱回读、事件状态校验和审计记录。
- **Demo 证据**：展示动作前后状态差异及每项断言的证据。

共享模型池和本地小模型 + 接口大模型的组合是工程优化点，不单独包装为产品创新；其价值要由成本、时延和效果测试支撑。

### 16.2 评价指标框架

| 评价维度 | 指标 | 建议测量方式 | 当前状态 |
|---|---|---|---|
| 事件发现 | 标杆事件检出率、正常样例误报率 | 先建立人工核验的正负样例集再重放；官方 data 当前没有正常组/完整标签 | 【待设计】样例集、标注流程与目标值 |
| 证据关联 | 关键证据引用完整率、错误关联率 | 与标注攻击链比对 | 【待设计】关联规则与口径 |
| 调查质量 | 事实项准确率、未决项标注率 | 结构化输出逐字段评分 | 【待设计】评分集 |
| 权限隔离 | 越权工具调用阻断率 | 主动构造越权测试 | 目标应为 100%，需实测证明 |
| 高风险控制 | 未审批高风险动作执行次数 | 审计日志与状态回读 | 目标为 0 |
| 审计完整性 | 关键节点审计覆盖率 | 对照流程节点核验 | 【待设计】覆盖口径 |
| 闭环验证 | 旧 Key、新 Key、恶意调用、合法业务四类断言通过率 | 重放 Demo 并查询真实 Mock/沙箱状态 | 【待设计】目标值 |
| 系统性能 | 端到端时延、各模型时延、资源占用 | 多轮重复运行 | 【待验证】 |
| 演示稳定性 | 五分钟流程成功率 | 连续完整演示测试 | 【待设计】轮次与目标值 |

官方文件名只能作为弱标签候选，不能直接充当 ground truth。不能在没有人工核验数据集、计算口径和实测记录时宣称具体准确率或领先水平。

## 17. 当前边界、扩展路线与比赛映射

### 17.1 第一阶段最小开发闭环（Golden Path）

后续开发第一阶段只需稳定证明以下唯一主路径：

```text
Official/Synthetic 数据能够进入
  → 产生带 EvidenceReference 的 Security Signal
  → 创建 SecurityIncident
  → 主代理产生受限 AgentTask
  → 调查子代理获得 Evidence 并返回 Agent Finding
  → 溯源子代理产生带引用的 Timeline
  → 主代理形成 Action Recommendation
  → 操作执行子代理产生 ActionRequest
  → PolicyDecision 阻止直接执行
  → 人工批准
  → Mock/沙箱状态真实改变并产生 ExecutionResult
  → VerificationResult 全部通过
  → AuditRecord 完整，事件进入 CLOSED
```

第一版验收重点是数据来源真实、状态真实推进、权限不能绕过和结果可回查，不是 Agent 数量、模型数量或前端动画效果。失败重规划、复杂 RAG、多云和高级治理在 Golden Path 稳定后再增加。

### 17.2 当前必须开发的最小范围

【已确认】

- 一个云平台适配范围；
- 一个租户事件模型；
- 一类 API Key；
- 一条 CI Action 篡改到 API 滥用的攻击链；
- 一个静默监测子代理；
- 一个负责调度和用户交互的主代理；
- 事件调查、攻击溯源、操作执行和审计汇报子代理接口；
- LangGraph 调度框架和事件状态中枢；
- 确定性策略、人工审批和审计；
- Mock 或沙箱化的冻结、轮换和恢复验证；
- 一个五分钟内可理解、可复现的最小前端。
- 一个能读取官方 PCAP/PCAP-NG、生成规范化网络事件与 EvidenceReference 的离线重放入口；
- Official/Synthetic/Mock/System 四类来源的结构化标识和界面展示；
- 一小组经过人工核验的官方样本，用于解析、规则和证据回查验收，不直接训练模型。

### 17.3 当前明确不做

- 真实生产凭据和未经授权的数据访问；
- 任意 Shell 执行和自动修改真实生产资源；
- 完整 SIEM、SOAR、EDR、IAM 或 CWPP；
- 端点隔离、横向移动响应和所有凭据泄露来源；
- 多个无边界通用 Agent 自由协作；
- 让模型直接决定权限或执行高风险动作；
- 宣称已经覆盖多云、多租户类型、多行业和全场景攻击。
- 把全部官方 PCAP 未经标注直接用于模型训练，或把文件名当作完整 ground truth；
- 伪造跨 PCAP 关联，把 Synthetic 说成官方数据，或把 Mock 说成生产处置。

### 17.4 已确认的模型池与产品用途

【已确认】当前方案采用三类本地小模型与一个接口大模型的共享模型池，避免每个 Agent 独占模型服务：

| 模型 | 产品用途 | 必须验证的风险 |
|---|---|---|
| SecureBERT2.0 | 静默监测中的安全事件分类、字段和异常类型识别 | 英文安全语料优势能否迁移到本项目中文/结构化事件 |
| Qwen3-4B | 调查事实整理、操作申请生成、审计汇报 | 结构化输出稳定性、时延和资源占用 |
| BGE-M3 + bge-reranker-v2-m3 | 溯源证据检索、相似事件召回和时间线排序 | 检索质量、排序一致性和证据可追溯性 |
| deepseek-v4-flash 接口模型 | 主代理理解告警/指令、选择子代理、编排和汇总 | 接口可用性、成本、时延和结构化调度稳定性 |

【待验证】复杂事件是否切换 `deepseek-v4-pro`、是否进行小模型安全微调，以及最终模型版本，均不在当前设计中写死。模型名称是当前开发配置，不构成不可替换的产品定义。

### 17.5 待验证和待设计清单

### 17.6 扩展路线

扩展应遵循“先复用当前闭环，再增加适配面”的顺序：

1. **凭据类型扩展**：从单一 API Key 扩展到 Token、云访问密钥和服务账号凭据；
2. **云平台扩展**：增加连接器、审计字段映射和受控操作适配；
3. **泄露来源扩展**：覆盖代码仓库、镜像、构建日志和其他自动化组件；
4. **安全事件扩展**：在相同权限隔离与状态机制下增加新的调查和响应链路；
5. **治理扩展**：逐步建设 Agent 身份、工具供应链验证、异常行为监控和更完整的熔断能力。

每项扩展都必须重新回答数据是否授权、动作是否可控、结果是否可验证，不因接口形式通用就宣称场景已经覆盖。

## 18. 最终产品价值表述

> 御盾智核面向云服务商安全运营团队，围绕租户 API 凭据泄露后的异常使用、影响分析和安全响应，将 CI 安全事件、云 API 审计、认证流量、资源操作和凭据状态组织为同一安全事件。系统由主代理统一调度监测、调查、溯源、操作执行和审计汇报子代理，以职责、数据和权限隔离限制单个 Agent 的风险；模型负责分析与建议，确定性策略和人工审批负责高风险动作放行，受控接口和状态回读负责证明处置与恢复结果。

> 御盾智核不以“大模型替代安全设备”为目标，而是把分散的数据、工具和人员决策组织成一个证据可复核、权限可约束、动作可审批、结果可验证、过程可追溯的安全事件闭环。
